# 🔗 홀드 짝 맞추기 — 감지 · 검사 · 표시 사양

> [!NOTE]
> 에디터가 **키음이 들고 있는 "역할"을 읽어 홀드의 시작과 끝을 짝짓고**, 그 구간을 격자에 몸통으로 그리고,
> 짝이 어긋난 자리를 편집 중에 지목하는 기능의 사양입니다.
>
> **이 문서에는 게임 이름이 나오지 않습니다.** 게임마다 다른 값(어떤 키음이 시작인지, 키워드가 무엇인지)은
> 전부 [🎮 게임 프로파일](game_profiles.md) 의 표와 프로파일 파일에 있습니다.
> 게임이 늘어나도 이 문서는 바뀌지 않습니다 — 그게 이 문서를 따로 둔 이유입니다.
>
> 배경과 실측 기록: [⏱️ 채보 작성 시간 — 경고와 개선 과제](../issues/authoring_time.md)

> [!IMPORTANT]
> **구현 현황 (v0.1.4):** 짝 맞추기 엔진 · 검사기 · 몸통 표시(§11 의 P1~P3)는 구현돼 있습니다.
> **팔레트 역할 뱃지(P0)와 드래그로 홀드 배치(P4)는 아직 없습니다.**
> 코드 위치: [`HoldPairingEngine`](../../bms%20editer/Services/Holds/HoldPairingEngine.cs) ·
> [`HoldRoleClassifier`](../../bms%20editer/Services/Holds/HoldRoleClassifier.cs) ·
> [`HoldPolicies`](../../bms%20editer/Services/Holds/HoldPolicies.cs) ·
> [`GameProfileCatalog`](../../bms%20editer/Services/Holds/GameProfileCatalog.cs) ·
> 모델 [`GameProfile`](../../bms%20editer/Models/GameProfile.cs) · [`HoldModels`](../../bms%20editer/Models/HoldModels.cs)

## 1. 범위

### 푸는 것

* 건반 채널에 **단노트 2개로 찍혀 있는** 홀드의 시작·끝을 짝짓는다.
* 짝지어진 구간을 격자에 **몸통(Body)** 으로 이어 그린다.
* 짝이 어긋난 자리를 **편집할 때마다** 검사해 목록으로 보여준다. 게임을 켜지 않고 잡는다.
* 같은 기계로 **샌드백·연타·게이트·아크**처럼 "시작과 끝이 한 쌍인 모든 오브젝트"를 함께 다룬다.

### 안 푸는 것 (Non-goals)

| 안 하는 것 | 이유 |
|:---|:---|
| 표준 LN 채널 `51~59` · `#LNOBJ` | [`BmsParser`](../../bms%20editer/Services/BmsParser.cs) 의 편집 대상은 `16,11,12,13,14,15,18` 뿐이고 `5x` 는 `PreservedLines` 로 통과만 한다. 편집 대상이 되는 날 별도로 다룬다 |
| 파일을 "정규 형식"으로 **변환** | 원문 보존이 우선이다. 이 기능은 **읽고 보여주기만** 한다 (→ §3) |
| 조건 블록(`#RANDOM`/`#IF`)의 갈래를 건너는 짝 | 한 번에 한 갈래만 연주된다. 엔진은 `BranchId` 가 다른 노트끼리 절대 짝짓지 않는다 |
| 온셋 기반 자동 배치 | 온셋은 "소리가 튄 순간"만 알아서 홀드를 잡을 수 없다. [authoring_time.md 의 🅿️ 항목](../issues/authoring_time.md) |

## 2. 역할을 읽는 자리는 넷, 짝 짓는 방식은 다섯

BMS 에서 "이 노트가 홀드의 시작/끝"이라고 적을 수 있는 자리는 물리적으로 몇 군데 없습니다.
프로파일의 `role.type` 이 그중 하나를 고릅니다.

| `role.type` | 무엇을 읽는가 | 시작/끝을 정하는 것 |
|:---|:---|:---|
| **`KeyValue`** | 슬롯 코드 **값** 자체 (`headKeys` / `tailKeys`) | 값 |
| **`FileNameKeyword`** | 그 코드가 가리키는 **`#WAV` 파일명**의 키워드 | 키워드 |
| **`FileNameBase`** | 파일명에서 끝 표식(`stripSuffixes`)을 뗀 **기본명**으로 종류만 정한다 | **출현 순서** |
| **`FileNameUid`** | 파일명 앞자리 **UID** 로 종류만 정한다 (`uidTable`) | **출현 순서** |

아래 둘은 파일명이 종류(홀드냐 샌드백이냐)만 정하고, 시작/끝은 **같은 레인에서 그 종류가 몇 번째로 나왔는지**로 정합니다.
그래서 이 둘은 짝 정책 `Alternate` 와만 함께 쓸 수 있고, 나머지 둘은 `Alternate` 가 아닌 정책과만 씁니다.
어긋난 조합은 프로파일을 읽을 때 거부합니다(`GameProfileCatalog.Validate`).

짝 정책(`policy`)은 다섯 가지이고 §5 에 있습니다. 전부 실제 게임 모드 코드에 있던 방식입니다.

> 새 게임은 거의 확실히 이 조합 중 하나에 들어갑니다. 그래서 게임당 비용이 `코드 +0 / 데이터 +1` 입니다.
> 알려진 예외 가능성: 길이를 키음에 직접 인코딩하는 방식(`hold_4beat.wav` 처럼 끝 노트가 아예 없는 형태)은
> 짝지을 상대가 없어 새 방식이 필요합니다. 아직 사례가 없습니다.

## 3. 핵심 결정 ① — 게임은 소비하고, 에디터는 보존한다

게임의 런타임 파서는 짝이 맞은 **끝 노트를 자기 목록에서 지웁니다.** 안 지우면 홀드 끝 지점에 유령 단타가 하나 더 스폰되기 때문입니다. 이건 게임이 **한 번 읽고 버리는** 쪽이라 할 수 있는 일입니다.

**에디터는 반대로 해야 합니다.** [`BmsWriter`](../../bms%20editer/Services/BmsWriter.cs) 는 `chart.Notes` 의 **노트 하나당 슬롯 하나**를 찍습니다. `Type` 도, 홀드 길이도 보지 않습니다. 끝 노트를 목록에서 빼면 **저장하는 순간 파일에서 사라집니다.**

> [!CAUTION]
> 게임 파서의 "흡수 / 목록에서 제거" 동작을 에디터 동작으로 베껴 오면 차트가 망가집니다.
> 게임은 버리는 쪽이고, 에디터는 **다시 써야 하는** 쪽입니다.

### 그래서: `Chart.Notes` 를 건드리지 않는다

홀드는 노트를 고쳐 만드는 것이 아니라, 노트 **위에 얹는 파생 정보**입니다.

```csharp
// Models/HoldModels.cs
// 짝지어진 홀드 한 개. 노트 두 개를 "가리키기만" 한다.
// Kind 는 프로파일 규칙이 붙인 이름("Hold", "Sandbag", "Gate", "Fairy" ...)이다.
// 게임마다 짝을 이루는 오브젝트 종류가 달라서 열거형으로 못 박지 않는다.
public readonly record struct HoldLink(BmsNote Head, BmsNote Tail, string Kind);
```

얻는 것:

* **왕복 안전이 공짜다.** `BmsWriter` 를 한 줄도 고치지 않으므로 저장 경로에 새 위험이 생기지 않는다.
* `BmsNote` 에 `EndMeasure`/`EndPosition` 같은 필드를 **추가하지 않아도 된다.**
* 프로파일이 틀렸을 때 **파일이 아니라 화면만 틀린다.** 끄면 원래대로 돌아온다.

이건 이 저장소가 이미 쓰는 태도와 같습니다 — `PreservedLines`(모르는 줄은 원문 보존), `IsPathGuessed`(추측 결과는 파일에 박지 않음).

### 불변식 (구현이 지켜야 하는 선)

| # | 불변식 | 확인하는 테스트 |
|:--:|:---|:---|
| **I-1** | 홀드 감지는 **저장 결과에 영향을 주지 않는다.** 경로로 추정한 프로파일은 파일에 적지 않고, 저장했다 다시 읽어도 짝이 같다 | `HoldDocumentTests.경로로_추정한_프로파일은_…`, `RealGameChartTests.저장했다_다시_읽어도_…` |
| **I-2** | 프로파일이 없으면 감지 0개이고, 화면·저장이 이 기능 도입 전과 **완전히 같다** | `HoldPairingTests.프로파일이_없으면_아무것도_짝짓지_않는다` |
| **I-3** | 링크 표는 언제든 **버리고 다시 만들 수 있다.** 유일한 진실은 `Chart.Notes` 다 | `HoldPairingTests.짝_맞추기는_노트를_바꾸지_않는다` |

> 검색 창의 "롱" 필터는 노트 종류가 아니라 **링크 표**로 판정합니다(`MainWindowViewModel.IsHoldNote`).
> 짝지어진 홀드가 없으면 필터가 잠기고 "게임 프로파일을 고르면 홀드 짝을 읽습니다" 라고 안내합니다.

## 4. 핵심 결정 ② — 엔진은 "레인 단위 시퀀스"를 본다

`Resolve(wavKey, fileName) -> 역할` 같은 **노트 하나짜리 함수로는 출현 순서 방식을 담을 수 없습니다.** 역할이 키음만으로 정해지지 않고 **그 레인에서 몇 번째로 나왔는지**에 달려 있기 때문입니다.
그래서 엔진은 규칙마다 노트를 모아 **줄 하나(레인 또는 전체)의 시간순 목록**을 만든 뒤 정책에 넘깁니다.

```csharp
// Services/Holds/HoldPairingEngine.cs
HoldPairingResult Pair(IReadOnlyList<BmsNote> notes,
                       IReadOnlyDictionary<string, string> wavTexts,  // 키 -> #WAV 에 적힌 글자 그대로
                       GameProfile? profile);
```

규칙(`holdRules[]`) 하나마다:

1. `channels` 에 든 채널의 노트만 본다(비어 있으면 모든 편집 채널).
2. `HoldRoleClassifier` 가 노트마다 역할을 정한다: `Head` / `Tail` / `Member`(순서로 정해질 수열 구성원) / 무관.
3. **`BranchId` 와 레인으로** 묶는다. `scope: "AllChannels"` 이면 레인을 가리지 않고 한 줄로 묶는다.
4. 시각(`Measure + Position`)으로 정렬한다. 같은 자리면 `FifoQueue` 만 시작을 앞에 두고, 나머지는 파일에 적힌 순서를 따른다.
5. `HoldPolicies.Apply` 가 정책대로 짝과 진단을 낸다.

### 키 비교는 정규화한 뒤에 한다

프로파일은 키를 `"02"` 처럼 적지만 차트는 3자리 모드일 수 있습니다(`"002"`).
`NormalizeKey` 는 **대문자로 올리고 앞의 0 을 떼서** 자릿수와 무관하게 같은 문자열로 만든 뒤 비교합니다.
2자리 프로파일과 3자리 프로파일이 **둘 다 존재**하므로 이건 선택이 아닙니다.

## 5. 짝 정책 (`policy`)

비슷해 보여도 합치면 안 됩니다. **시작 두 개 뒤에 끝 하나가 오는** 같은 배치를 두고 정책마다 결과가 다릅니다.
에디터가 게임과 다르게 짝지으면 화면의 몸통이 게임과 다른 곳을 가리킵니다.

| 정책 | 규칙 | 시작 둘 · 끝 하나일 때 |
|:---|:---|:---|
| **`NearestUnconsumedTail`** (기본) | 시작마다, 그 **뒤**에 있는 아직 안 쓴 끝 중 가장 가까운 것 하나. 끝은 한 번만 쓴다 | 앞 시작이 끝을 가져가고 뒤 시작은 고아 |
| **`NearestTailShared`** | 시작마다, 그 뒤의 가장 가까운 끝. 끝을 **소비하지 않는다** | 두 시작이 끝 하나를 같이 쓴다 (`SharedTail` 주의) |
| **`FifoQueue`** | 시작을 줄 세우고, 끝이 올 때마다 가장 오래 기다린 시작과 짝. 끝이 시작보다 앞서지 않으면 **둘 다 버린다** | 앞 시작과 짝, 뒤 시작은 고아 |
| **`ReplacePending`** | 대기 칸이 **하나뿐**이다. 끝이 오기 전에 시작이 또 오면 앞 시작을 버리고 바꿔 끼운다 | 뒤 시작이 끝을 가져가고 앞 시작은 버려짐 (`ReplacedHead`) |
| **`Alternate`** | 파일명의 시작/끝 표식을 보지 않고, 같은 종류가 나온 순서로 홀수=시작, 짝수=끝 | 1번째 시작 ↔ 2번째(시작이라고 적혔어도 끝), 끝은 새 수열의 시작 |

공통:

1. **줄(레인)별로 독립**입니다. 다른 레인과는 짝짓지 않습니다(`AllChannels` 규칙만 예외).
2. **마디 경계는 무관**합니다 — 마디를 넘는 홀드는 정상입니다.
3. 같은 자리의 끝은 짝이 아닙니다(`NearestUnconsumedTail`·`NearestTailShared` 는 "시작보다 뒤"만 본다).
4. 끝까지 남은 시작과, 짝지을 시작이 없던 끝은 **고아**입니다. §7 진단으로 올립니다.

> [!IMPORTANT]
> 게임이 대기 칸을 **하나만** 두는 경우(`ReplacePending`) 에디터도 그대로 흉내 냅니다. 다만 **버려지는 시작을 조용히
> 흘려보내지 않고** `ReplacedHead` 로 지목합니다. 게임에서는 그 시작이 소리 없이 사라지는데, 그게 바로 검사기가 잡아야 할 자리입니다.

## 6. 판별 방식별 명세

### `KeyValue` — 슬롯 코드 값으로 판정

```json
"role": { "type": "KeyValue", "headKeys": [ "02" ], "tailKeys": [ "03" ] }
```

* 키 집합 대 집합입니다. **N:M 을 허용해야 합니다** — 시작 8종이 끝 2종 중 아무것으로나 닫히는 프로파일이 실제로 있습니다.
* 휴리스틱이 전혀 없습니다. 오검출도 미검출도 구조적으로 생기지 않습니다.
* 같은 프로파일 안에 `kind` 별로 규칙을 여러 개 둘 수 있습니다(홀드 / 게이트 / 아크).

### `FileNameKeyword` — 파일명 키워드로 판정

```json
"role": {
  "type": "FileNameKeyword",
  "requiredKeyword": "hold",
  "headKeywords": [ "홀드 시작", "hold start", "hold_start", "ln start" ],
  "tailKeywords": [ "홀드 끝",   "hold end",   "hold_end",   "ln end" ],
  "tailFirst": true
}
```

지켜야 하는 것 네 가지입니다. 전부 실제 게임 규칙에서 나왔습니다:

| 규칙 | 왜 |
|:---|:---|
| **부분 일치**, 대소문자 무관. 끝 앵커(`$`)를 쓰지 않는다 | 실제 파일명이 `hihat_1 홀드 시작.wav` 처럼 키워드 뒤에 확장자만 있거나, `hold_start_01.wav` 처럼 뒤에 더 붙는다 |
| **구분자를 가정하지 않는다** | 공백 · `_` · `-` · 없음이 전부 실제로 쓰인다. 키워드 목록에 변형을 전부 적는다 |
| **한글 키워드를 포함한다** (`홀드`/`시작`/`끝`) | 실제 프로파일 두 곳이 한글 키워드를 쓴다 |
| **검사 순서를 명시한다** (`tailFirst`) | 양쪽 키워드를 다 담은 파일명이 실제로 존재한다. 게임마다 검사 순서가 반대다 |

`requiredKeyword` 가 있으면 그 글자가 없는 파일은 전부 일반 노트입니다.

> [!CAUTION]
> **단일 문자·범용 접미사(`_s`, `_e`, `_in`, `_out`)를 기본 키워드에 넣지 마십시오.**
> `fade_out.wav`, `kick_in.wav`, `intro_s.wav` 가 전부 홀드로 걸립니다.
> 게다가 어떤 프로파일은 파일명 접미사를 **이미 다른 의미로** 씁니다(오프셋 델타 `_dt0.7`).

> [!NOTE]
> **BaseName 대칭을 강제하지 않습니다.** 실제 규칙은 "같은 채널의 아무 끝이나 시작을 닫는다" 입니다.
> `hihat_1 홀드 시작` ↔ `hihat_2 홀드 끝` 조합을 게임은 정상 매칭하는데 에디터만 고아로 경고하면 **거짓 경보**입니다.

### `FileNameBase` — 기본명으로 종류, 순서로 시작/끝

```json
"role": { "type": "FileNameBase", "baseNames": [ "Hold" ], "stripSuffixes": [ " end" ] }
```

1. 파일명(확장자 제외)에서 `stripSuffixes` 중 하나를 떼면 그 노트의 **표식**은 끝입니다.
2. 남은 이름이 `baseNames` 와 같아야(대소문자 무관) 이 규칙의 수열 구성원입니다.
3. 시작/끝은 `Alternate` 가 **순서로** 정합니다. 표식은 §7 `ParityBreak` 를 찾는 데만 씁니다.

### `FileNameUid` — UID 로 종류, 순서로 시작/끝

프로파일의 `uidTable` 이 게임 파서의 분기 순서를 그대로 옮깁니다. **순서가 곧 규칙**입니다.

1. `pattern` 으로 파일명 앞의 UID 를 뽑는다(0부터 센 `offset`/`length` 로 자리를 적는다. "몇 번째 자리" 표현은 모호하다).
2. `finalPrefixes` → `blockingKeywords` → 앞자리 `prefixTypes` → 타입 자리 `typeCodes` 순으로 종류를 정한다.
   앞자리가 타입 자리보다 **우선**입니다. 같은 UID 가 양쪽에 걸리는 조합이 실제로 존재합니다.
3. UID 로 정해지지 않았을 때만 `nameFallbacks`(이름 키워드)로 추정한다.
4. 종류가 규칙의 `kind` 와 같으면 수열 구성원이다. **종류가 다르면 수열을 따로 센다.**
5. 파일명의 `headLabels`/`tailLabels`(예: "시작"/"끝")는 짝을 정하지 않는다. `ParityBreak` 를 찾는 데만 쓴다.

> [!CAUTION]
> **출현 순서 방식만 "전파(cascade)" 가 있습니다.** 수열 중간에 홀드 하나를 끼워 넣으면
> **그 뒤의 모든 짝이 시작↔끝으로 뒤집힙니다.** 47마디를 고치고 60마디부터 무너지는 증상의 정체입니다.
> 그래서 검사기는 **"어긋난 모든 자리"가 아니라 "처음 어긋난 자리"를 지목합니다**(§7 `ParityBreak`).

## 7. 검사기 (Pair Linter)

### 진단 목록 (`HoldDiagnosticKind`)

| 진단 | 무엇 | 수준 | 나오는 정책 |
|:---|:---|:---:|:---|
| `OrphanHead` | 짝을 못 찾은 시작 | 🔴 | 전부 |
| `OrphanTail` | 짝을 못 찾은 끝 | 🔴 | `Alternate` 외 전부 |
| `ReplacedHead` | 끝이 오기 전에 시작이 또 나와 앞 시작이 버려졌다 | 🔴 | `ReplacePending` |
| `ParityBreak` | 파일명 표식과 출현 순서가 **처음** 어긋난 자리(규칙·레인마다 한 번만) | 🔴 | `Alternate` |
| `SharedTail` | 끝 하나를 시작 여러 개가 같이 쓴다 | 🟡 | `NearestTailShared` |
| `ZeroLength` | 시작과 끝이 같은 자리다 | 🟡 | `ReplacePending` · `Alternate` |

> 끝을 시작보다 앞으로 옮긴 경우(설계 때의 `ReversedPair`)는 따로 두지 않았습니다. 정책이 "시작보다 뒤의 끝"만 보므로
> 그 자리는 고아(`OrphanHead`/`OrphanTail`)로 드러납니다.

### 표시 규칙

* 진단 문장은 **"에디터가 무엇을 못 했는지"가 아니라 "게임에서 어떻게 될지"를 말합니다.** 프로파일 규칙의
  `orphanHeadOutcome` / `orphanTailOutcome` 문장이 메시지 뒤에 붙습니다. 게임 로그를 읽으러 가지 않게 하는 것이 목적입니다.
* 오른쪽 패널 목록에 `🔴 012마디 · 11 · 메시지` 형태로 보입니다. 항목을 고르면 그 노트를 선택하고
  **그 자리로 격자가 스크롤**됩니다(`SetNoteSelection(..., NoteSelectionSource.Search)`).
* 🔴 수준 노트는 격자에 **주황 점선 테두리**가 쳐집니다. 🟡 는 목록에만 나옵니다(경고가 풍경이 되지 않게).
* 상태 표시줄에 `홀드 짝 N개 · 🔴 문제 n · 🟡 주의 m` 이 보입니다. **저장을 막지는 않습니다** — 작업 중간에는 당연히 짝이 안 맞습니다.

### 언제 다시 도는가

* 노트 편집: [`NotifyNotesChanged()`](../../bms%20editer/ViewModels/MainWindowViewModel.Editing.cs) **단 한 곳**. 모든 편집 경로가 여기를 지납니다.
* 키음 표(`WavList`)가 바뀔 때 — 파일명으로 판별하는 규칙이 있어서입니다.
* 프로파일을 바꿀 때, 문서를 열거나 새로 만들 때.

항상 **전체 재계산**입니다. 비용은 노트 수에 대해 O(n log n) 이고 실측 규모(수백~천 노트)에서는 눈에 띄지 않습니다.
부분 갱신은 캐시가 어긋나는 버그를 부르므로, 느려지기 전까지는 전체 재계산이 맞습니다.

## 8. 표시 (Rendering)

### 홀드 몸통 ([`NoteGridControl.DrawHoldBodies`](../../bms%20editer/Views/Controls/NoteGridControl.cs))

* 시작·끝의 화면 좌표를 **각각** 노트와 같은 `ComputeNoteTPos`(= `ChartTimeline.SecondsAt(measure + position)`) 로 구합니다.
* **마디 단위 선형 보간으로 몸통을 늘리지 않습니다.** BPM 변화(`#xxx03`/`#xxx08`)나 변박(`#xxx02`) 구간을 지나는 홀드의 끝이 어긋납니다.
  [`bpm_sync_principles.md`](../architecture/bpm_sync_principles.md) 가 같은 이유로 만들어진 규칙입니다.
* 세로·가로 보기 둘 다 그립니다. 몸통은 레인 폭의 44% 로 레인 가운데에 놓여, 몸통 위의 다른 노트가 묻히지 않습니다.
* 종류(`Kind`)마다 색이 다릅니다: 홀드 노랑 · 샌드백 분홍 · 게이트 하늘 · 페어리 보라 · 더블 초록 · 연타 주황.
* 채널을 건너 맺어지는 짝(`AllChannels` 규칙)은 몸통 대신 **두 노트를 잇는 선**으로 그립니다.
* 몸통은 노트보다 먼저 그려서, 시작·끝 노트가 몸통 위에 올라옵니다.

### 팔레트 역할 뱃지 — ⬜ 아직 없음

[`BmsWavItem.DisplayText`](../../bms%20editer/Models/BmsWavItem.cs) 는 `#키: 파일명` 을 보여줍니다. 여기에 역할 뱃지(`▶시작` / `■끝`)를 붙이는 것이 계획입니다.

> 어떤 프로파일은 **시작이 뒤 글자, 끝이 앞 글자**입니다(`00B`=시작 / `00A`=끝).
> 팔레트에서 번호만 보고 고르면 뒤집힙니다. 지금은 뒤집어 찍으면 몸통이 안 생기고 고아 테두리가 뜨는 것으로 알 수 있습니다.
> **뱃지가 있으면 찍기 전에 막을 수 있습니다.** 출현 순서 방식은 키음만으로 역할이 정해지지 않으므로 뱃지 대상이 아닙니다.

## 10. 프로파일을 어디에 담고 어떻게 고르나

### 담는 자리 — 단일 exe를 깨지 않는다

[README.md](../../README.md) 는 *"이 exe만 복사하면 실행됩니다"* 를 약속합니다. 외부 JSON 폴더만 쓰면 이 약속이 깨집니다.

| 자리 | 쓰는 법 |
|:---|:---|
| `bms editer/Profiles/*.json` **내장** | csproj 의 `<EmbeddedResource Include="Profiles\*.json" LogicalName="profiles/…" />` 로 exe 안에 들어간다. AvaloniaResource 가 아닌 이유는 Avalonia 를 띄우지 않고도 단위 테스트가 바로 읽기 위해서다 |
| exe 옆 `profiles\*.json` **덮어쓰기** | 있으면 같은 id 의 내장 프로파일을 대체한다. **리빌드 없이 게임을 추가**할 수 있다 |

읽지 못한 프로파일은 목록에서 빠지고 이유가 `GameProfileCatalog.LoadErrors` 에 남습니다. 규칙이 빠졌거나
판별 방식과 정책이 맞지 않는 프로파일은 읽을 때 거부합니다 — "홀드가 하나도 안 잡히는" 조용한 실패를 막기 위해서입니다.

### 고르는 법 — 반드시 한 번에 하나

여러 프로파일을 동시에 적용하면 **오검출이 확정**입니다. 키음 `02` 는 어떤 게임에서 홀드 시작이지만 다른 게임에서는 그냥 2번 키음입니다.

차트가 자기 프로파일을 들고 다닙니다. 비표준 헤더 선례가 이미 있습니다 — `#BMSEDITER_OFFSET`.

```bms
#BMSEDITER_PROFILE deflate
```

| 출처(`HoldProfileOrigin`) | 언제 | 파일에 적나 |
|:---|:---|:---:|
| `Header` | 파일에 `#BMSEDITER_PROFILE` 이 있고 아는 id 다 | 그대로 |
| `UnknownHeader` | 헤더가 있지만 모르는 id 다. 짝은 읽지 않는다 | 원문 그대로 둔다 |
| `Path` | 헤더가 없고, 차트 경로의 폴더 이름이 `pathHints` 에 걸린다(가까운 폴더부터, 긴 힌트 우선) | **안 적는다** |
| `User` | 사용자가 드롭다운에서 골랐다 | 적는다 |
| `None` | 아무것도 없다 → 홀드 감지가 전부 꺼진다(불변식 I-2) | — |

게임 쪽 파서는 모르는 헤더를 무시하므로 주입에 영향이 없습니다.

* 값별 목록은 [game_profiles.md](game_profiles.md) 에 있고, 그 표는 JSON 을 옮긴 것입니다. **JSON 이 진실**입니다.

## 13. 드래그로 홀드 배치 — 입력 충돌을 먼저 풀어야 한다

"시작에서 끝까지 그으면 짝 2개가 자동 생성" 은 짝이 구조적으로 안 깨지게 하는 가장 좋은 방법이지만, **지금 입력과 정면으로 충돌합니다.**

* 편집 모드 좌클릭은 **누른 순간 즉시 배치**합니다([`NoteGridControl`](../../bms%20editer/Views/Controls/NoteGridControl.cs) `OnPointerPressed`).
* Ctrl/Shift + 드래그는 **범위 선택에 이미 할당**되어 있습니다.

| 선택지 | 장점 | 단점 |
|:---|:---|:---|
| (a) 별도 홀드 도구 토글 | 기존 감각을 건드리지 않는다 | 토글 왕복이 늘어난다 |
| **(b) "시작 찍고 → 끝 찍기" 2클릭** | 새 입력 규칙이 없다. 구현이 가장 가볍다 | 중간 상태(시작만 찍힌)를 보여줘야 한다 |
| (c) 편집 모드 좌클릭을 press-drag-release 로 | 가장 직관적 | **단타 배치 감각이 바뀐다.** 340개를 찍는 작업에서 이건 큰 변화다 |

현재 기울어져 있는 쪽은 **(b)** 입니다 — 기존 입력을 전혀 바꾸지 않고, 중간 상태는 고아 테두리를 그대로 씁니다.
