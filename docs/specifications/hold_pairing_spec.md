# 🔗 홀드 짝 맞추기 — 감지 · 검사 · 표시 사양

> [!NOTE]
> 에디터가 **키음이 들고 있는 "역할"을 읽어 홀드의 시작과 끝을 짝짓고**, 그 구간을 격자에 몸통으로 그리고,
> 짝이 어긋난 자리를 편집 중에 지목하는 기능의 사양입니다.
>
> **이 문서에는 게임 이름이 나오지 않습니다.** 게임마다 다른 값(어떤 키음이 시작인지, 키워드가 무엇인지)은
> 전부 [🎮 게임 프로파일](game_profiles.md) 의 표와 프로파일 파일에 있습니다.
> 게임이 늘어나도 이 문서는 바뀌지 않습니다 — 그게 이 문서를 따로 둔 이유입니다.
>
> 배경과 실측 기록: [⏱️ 채보 작성 시간 — 경고와 개선 과제](../issues/authoring_time.md)

---

## 1. 범위

### 푸는 것

* 건반 채널에 **단노트 2개로 찍혀 있는** 홀드의 시작·끝을 짝짓는다.
* 짝지어진 구간을 격자에 **몸통(Body)** 으로 이어 그린다.
* 짝이 어긋난 자리를 **편집할 때마다** 검사해 목록으로 보여준다. 게임을 켜지 않고 잡는다.
* 같은 기계로 **샌드백·연타·아크**처럼 "시작과 끝이 한 쌍인 모든 오브젝트"를 함께 다룬다.

### 안 푸는 것 (Non-goals)

| 안 하는 것 | 이유 |
|:---|:---|
| 표준 LN 채널 `51~59` · `#LNOBJ` | [`BmsParser`](../../bms%20editer/Services/BmsParser.cs) 의 편집 대상은 `16,11,12,13,14,15,18` 뿐이고 `5x` 는 `PreservedLines` 로 통과만 한다. 편집 대상이 되는 날 별도로 다룬다 |
| 파일을 "정규 형식"으로 **변환** | 원문 보존이 우선이다. 이 기능은 **읽고 보여주기만** 한다 (→ §3) |
| 조건 블록(`#RANDOM`/`#IF`) 안의 홀드 | 이미 `HasConditionalBlocks` 로 저장이 막혀 있다. 짝 맞추기는 `BranchId` 로 분리만 하고 건드리지 않는다 |
| 온셋 기반 자동 배치 | 온셋은 "소리가 튄 순간"만 알아서 홀드를 잡을 수 없다. [authoring_time.md 의 🅿️ 항목](../issues/authoring_time.md) |

## 2. 전략은 셋뿐이다

BMS에서 "이 노트가 홀드의 시작/끝"이라고 적을 수 있는 자리는 물리적으로 몇 군데 없습니다.

| 전략 | 역할을 어디서 읽는가 | 레인 문맥 필요? |
|:---|:---|:---:|
| **① KeyValue** | 슬롯 코드 **값** 자체 (`02`=시작, `03`=끝) | 아니오 |
| **② FileNameKeyword** | 그 코드가 가리키는 **`#WAV` 파일명**의 키워드 | 아니오 |
| **③ OccurrenceParity** | 같은 채널 안의 **출현 순서** (홀수=시작, 짝수=끝) | **예** |

현재 프로파일 5종이 이 셋을 **이미 전부 채웠습니다** ([game_profiles.md](game_profiles.md)).
새 게임은 거의 확실히 이 셋 중 하나에 들어갑니다 — **게임이 늘어도 전략은 늘지 않습니다.**
그래서 게임당 비용이 `코드 +0 / 데이터 +1` 입니다.

> [!NOTE]
> 알려진 예외 가능성: 길이를 키음에 직접 인코딩하는 방식(`hold_4beat.wav` 처럼 끝 노트가 아예 없는 형태)은
> 짝지을 상대가 없어 네 번째 전략이 필요합니다. 아직 사례가 없습니다. 나타나면 이 표에 한 줄 늘어납니다.

## 3. 핵심 결정 ① — 게임은 소비하고, 에디터는 보존한다

게임의 런타임 파서는 짝이 맞은 **끝 노트를 자기 목록에서 지웁니다.** 안 지우면 홀드 끝 지점에 유령 단타가 하나 더 스폰되기 때문입니다. 이건 게임이 **한 번 읽고 버리는** 쪽이라 할 수 있는 일입니다.

**에디터는 반대로 해야 합니다.** [`BmsWriter`](../../bms%20editer/Services/BmsWriter.cs) 는 `chart.Notes` 의 **노트 하나당 슬롯 하나**를 찍습니다. `Type` 도, 홀드 길이도 보지 않습니다. 끝 노트를 목록에서 빼면 **저장하는 순간 파일에서 사라집니다.**

> [!CAUTION]
> 게임 파서의 "흡수 / 목록에서 제거" 동작을 에디터 동작으로 베껴 오면 차트가 망가집니다.
> 게임은 버리는 쪽이고, 에디터는 **다시 써야 하는** 쪽입니다.

### 그래서: `Chart.Notes` 를 건드리지 않는다

홀드는 노트를 고쳐 만드는 것이 아니라, 노트 **위에 얹는 파생 정보**입니다.

```csharp
// 짝지어진 홀드 한 개. 노트 두 개를 "가리키기만" 한다.
// Chart.Notes 안의 노트는 위치도 키음도 그대로 남아 있으므로,
// BmsWriter 는 이 기능을 전혀 몰라도 원본과 같은 두 줄을 그대로 써낸다.
public readonly record struct HoldLink(BmsNote Head, BmsNote Tail, HoldKind Kind);

// 시작과 끝이 한 쌍인 오브젝트는 홀드만이 아니다. 짝 맞추는 기계는 하나로 쓴다.
public enum HoldKind { Hold, Sandbag, Arc }
```

얻는 것:

* **왕복 안전이 공짜다.** `BmsWriter` 를 한 줄도 고치지 않으므로 저장 경로에 새 위험이 생기지 않는다.
* `BmsNote` 에 `EndMeasure`/`EndPosition` 같은 필드를 **추가하지 않아도 된다.**
* 프로파일이 틀렸을 때 **파일이 아니라 화면만 틀린다.** 끄면 원래대로 돌아온다.

이건 이 저장소가 이미 쓰는 태도와 같습니다 — `PreservedLines`(모르는 줄은 원문 보존), `IsPathGuessed`(추측 결과는 파일에 박지 않음).

### 불변식 (구현이 지켜야 하는 선)

| # | 불변식 |
|:--:|:---|
| **I-1** | 프로파일을 켜고 차트를 **열었다 바로 저장하면 바이트가 동일하다.** 홀드 감지는 저장 결과에 영향을 주지 않는다 |
| **I-2** | 프로파일이 없으면 감지 0개이고, 화면·저장이 이 기능 도입 전과 **완전히 같다** |
| **I-3** | 링크 표는 언제든 **버리고 다시 만들 수 있다.** 유일한 진실은 `Chart.Notes` 다 |

> [!NOTE]
> **기존 "롱" 필터 연동:** [`NoteSearchViewModel`](../../bms%20editer/ViewModels/NoteSearchViewModel.cs) 의 `isLong` 판정은
> 지금 `note.Type` 을 봅니다. 링크 표 방식에서는 `Type` 이 계속 `Normal` 이므로,
> **판정을 "이 노트가 링크 표의 Head/Tail인가" 로 바꿔야** 필터가 동작합니다.
> 같은 자리의 `AreNoteTypeFiltersUsable` 잠금과 힌트 문구(*"아직 롱노트·숨김 노트를 편집 대상으로 읽지 않습니다"*)도 함께 고쳐야 합니다.

## 4. 핵심 결정 ② — 전략 인터페이스는 "레인 단위 시퀀스"다

`Resolve(wavKey, fileName) -> 역할` 같은 **노트 하나짜리 함수로는 전략 ③을 담을 수 없습니다.** 출현 순서 방식은 역할이 키음만으로 정해지지 않고 **그 레인에서 몇 번째로 나왔는지**에 달려 있기 때문입니다.

그래서 경계를 한 단계 위로 올립니다. 전략은 **레인 하나의 시간순 노트 목록**을 받아 짝과 진단을 돌려줍니다.

```csharp
public interface IHoldPairingStrategy
{
    // laneNotes: 한 레인(채널)의 노트를 시간 순으로 정렬한 것.
    //            BranchId 가 섞이지 않게 미리 갈라서 넘긴다.
    HoldPairingResult PairLane(IReadOnlyList<BmsNote> laneNotes, HoldPairingContext context);
}

public sealed record HoldPairingResult(
    IReadOnlyList<HoldLink> Links,
    IReadOnlyList<HoldDiagnostic> Diagnostics);

// 전략이 키음을 해석할 때 필요한 것들. 차트마다 달라지므로 주입한다.
public sealed record HoldPairingContext(
    IReadOnlyDictionary<string, string> WavTable, // 키 -> 파일명
    int KeyWidth,                                 // WavKey.WidthOf(chart) · 2 또는 3
    GameProfile Profile);
```

전략 ①②는 "역할 판정" 부분만 다르고 짝 맞추는 규칙이 같으므로 **공용 페어링(§5)을 공유**합니다. 전략 ③만 자체 구현입니다.

### 키 비교는 정규화한 뒤에 한다

프로파일은 키를 `"02"` 처럼 적지만 차트는 3자리 모드일 수 있습니다(`"002"`). **대문자로 올리고 차트의 `KeyWidth` 로 좌측 0 패딩한 뒤** 비교해야 합니다. [`WavKey.WidthOf`](../../bms%20editer/Services/WavKey.cs) 가 그 폭을 알고 있고, 파서는 이미 코드를 `.ToUpper()` 해서 넣습니다. 실제로 2자리 프로파일과 3자리 프로파일이 **둘 다 존재**하므로 이건 선택이 아닙니다.

## 5. 공용 역할 페어링 규칙

전략 ①②가 역할(`Head`/`Tail`/`Normal`)을 판정한 뒤 공통으로 적용하는 규칙입니다.

1. **레인(채널)별로 독립**입니다. 다른 레인의 노트와는 절대 짝짓지 않습니다.
2. 시간순으로 훑습니다. **마디 경계는 무관**합니다 — 마디를 넘는 홀드는 정상입니다.
3. `Head` 를 만나면 **대기 목록에 쌓습니다.** 덮어쓰지 않습니다.
4. `Tail` 을 만나면 대기 목록에서 하나를 골라 짝짓습니다. 고르는 기준은 프로파일의 `nestingPolicy`:

   | 값 | 고르는 것 | 쓰는 데 |
   |:---|:---|:---|
   | **`Fifo`** (기본) | 가장 **오래 기다린** Head | 중첩을 허용하지 않는 게임. "Head 기준 가장 가까운 Tail"과 같은 결과가 된다 |
   | `Lifo` | 가장 **최근** Head | 홀드 중첩을 지원하는 게임 |
   | `Reject` | 대기 Head가 2개 이상이면 짝짓지 않고 진단만 올림 | 중첩이 곧 오류인 게임 |

5. 한 번 짝지어진 `Head`/`Tail` 은 **재사용되지 않습니다.**
6. 끝까지 남은 대기 `Head` 와, 짝지을 `Head` 가 없던 `Tail` 은 **고아**입니다. 둘 다 §7 의 진단으로 올립니다.

> [!IMPORTANT]
> **3번이 핵심입니다.** 대기 칸을 `pending[lane] = note` 처럼 **한 칸**으로 두면, 같은 시작 키음이 두 번 연달아 나올 때
> 앞의 것이 **조용히 버려집니다.** 그게 바로 검사기가 잡아야 할 고아인데, 증거가 먼저 사라집니다.
> 대기 목록은 반드시 **여러 개를 담을 수 있어야** 합니다.

## 6. 전략별 명세

### ① KeyValue — 슬롯 코드 값으로 판정

```
headKeys: ["02"]            tailKeys: ["03"]
```

* 키 집합 대 집합입니다. **N:M 을 허용해야 합니다** — 시작 8종이 끝 2종 중 아무것으로나 닫히는 프로파일이 실제로 있습니다. `(BaseName, StartKey, EndKey)` 같은 1:1 레코드로는 표현할 수 없습니다.
* 휴리스틱이 전혀 없습니다. 오검출도 미검출도 구조적으로 생기지 않습니다. **그래서 제일 먼저 구현합니다.**
* 같은 프로파일 안에 `HoldKind` 별로 여러 쌍을 둘 수 있습니다(홀드 / 아크).

### ② FileNameKeyword — 파일명 키워드로 판정

```
requiredKeyword: "hold"              // 있으면, 이 키워드가 없는 파일은 전부 Normal (선택)
headKeywords: ["홀드 시작", "hold start", "hold_start", "ln start", ...]
tailKeywords: ["홀드 끝",   "hold end",   "hold_end",   "ln end",   ...]
tailFirst: true                      // 한 파일명이 양쪽을 다 담으면 Tail 로 판정
```

지켜야 하는 것 네 가지입니다. 전부 실제 게임 규칙에서 나왔습니다:

| 규칙 | 왜 |
|:---|:---|
| **부분 일치**. 끝 앵커(`$`)를 쓰지 않는다 | 실제 파일명이 `hihat_1 홀드 시작.wav` 처럼 키워드 뒤에 확장자만 있거나, `hold_start_01.wav` 처럼 뒤에 더 붙는다. 접미사 앵커는 둘 다 놓친다 |
| **구분자를 가정하지 않는다** | 공백 · `_` · `-` · 없음이 전부 실제로 쓰인다. `[_-]` 만 받으면 공백으로 띄운 파일명을 통째로 놓친다 |
| **한글 키워드를 포함한다** (`홀드`/`시작`/`끝`) | 실제 프로파일 두 곳이 한글 키워드를 쓴다 |
| **검사 순서를 명시한다** (`tailFirst`) | 양쪽 키워드를 다 담은 파일명이 실제로 존재한다. 순서 규칙이 없으면 판정이 구현 순서에 따라 달라진다 |

> [!CAUTION]
> **단일 문자·범용 접미사(`_s`, `_e`, `_in`, `_out`)를 기본 키워드에 넣지 마십시오.**
> `fade_out.wav`, `kick_in.wav`, `intro_s.wav` 가 전부 홀드로 걸립니다.
> 게다가 어떤 프로파일은 파일명 접미사를 **이미 다른 의미로** 씁니다(오프셋 델타 `_dt0.7`).
> 꼭 필요하면 그 프로파일에서만 켜십시오.

> [!NOTE]
> **BaseName 대칭을 강제하지 않습니다.** 실제 규칙은 "같은 채널의 아무 `Tail` 이나 `Head` 를 닫는다" 입니다.
> `hihat_1 홀드 시작` ↔ `hihat_2 홀드 끝` 조합을 게임은 정상 매칭하는데 에디터만 고아로 경고하면 **거짓 경보**입니다.
> BaseName 일치는 프로파일 옵션(`requireMatchingBaseName`)으로 두고 **기본값은 끔**입니다.
> 켠 프로파일에서는 어긋난 조합을 `BaseNameMismatch` 진단(경고 수준)으로만 올립니다.

### ③ OccurrenceParity — 출현 순서로 판정

```
holdClassRules: [ { offset: 2, length: 2, values: ["02"], kind: "Hold"    },
                  { offset: 2, length: 2, values: ["04"], kind: "Sandbag" } ]
prefixRules:    [ { offset: 0, length: 4, values: ["0004"], kind: "None"  } ]  // 타입 자리보다 우선
```

1. 레인 안에서 **"홀드 대상" 키음만** 골라 부분 수열을 만듭니다. 일반 단타는 순서 계산에 **끼지 않습니다.**
2. 그 수열의 **홀수 번째 = 시작, 짝수 번째 = 끝**입니다.
3. `HoldKind` 가 다른 것끼리는 **수열을 따로 셉니다.** 홀드와 샌드백을 한 줄로 세면 서로 닫아 버립니다. → 이 전제는 아직 미검증입니다(§12 Q1).
4. 숫자 위치는 **0-based `offset` 과 `length` 로 못 박습니다.** 가이드의 "몇 번째 자리" 표현은 한 자리 단위인지 두 자리 묶음 단위인지 모호합니다(§12 Q2). 프로파일에는 모호하지 않은 형태로만 적습니다.
5. 앞자리 프리픽스 규칙이 타입 자리 규칙보다 **우선**입니다. 같은 UID가 양쪽에 걸리는 조합이 실제로 존재합니다.

> [!CAUTION]
> **이 전략만 "전파(cascade)" 가 있습니다.** 수열 중간에 홀드 하나를 끼워 넣으면
> **그 뒤의 모든 짝이 시작↔끝으로 뒤집힙니다.** 47마디를 고치고 60마디부터 무너지는 증상의 정체입니다.
> 그래서 검사기는 **"어긋난 모든 자리"가 아니라 "처음 어긋난 자리"를 지목해야** 합니다(§7 `ParityBreak`).
> 뒤집힌 60마디를 백 줄 늘어놓는 것은 도움이 되지 않습니다. 원인은 47마디 한 곳입니다.

## 7. 검사기 (Pair Linter)

### 진단 목록

| 진단 | 무엇 | 수준 | 게임에서는 어떻게 되는가 |
|:---|:---|:---:|:---|
| `OrphanHead` | 짝을 못 찾은 시작 | 🔴 | **단타로 강등**되어 스폰된다 |
| `OrphanTail` | 짝을 못 찾은 끝 | 🔴 | 무시되거나 유령 단타가 된다 |
| `ParityBreak` | 출현 순서 수열이 **처음** 어긋난 자리 | 🔴 | **이 지점 이후 전부 뒤집힌다** |
| `ReversedPair` | 끝이 시작보다 앞에 있다 | 🔴 | 길이가 음수가 된다. 노트를 옮긴 뒤 생긴다 |
| `ZeroLengthHold` | 시작과 끝이 같은 자리 | 🟡 | 길이 0 홀드. 게임에서 안 보일 수 있다(§12 Q4) |
| `NestingRejected` | `Reject` 정책에서 대기 Head가 2개 이상 | 🟡 | 중첩을 지원하지 않는 게임이다 |
| `BaseNameMismatch` | 짝의 BaseName이 다르다 (옵션 켠 경우만) | 🟡 | 게임은 정상 매칭한다. 의도 확인용 |

### 표시 규칙

* 진단은 **"에디터가 무엇을 못 했는지"가 아니라 "게임에서 어떻게 될지"를 말합니다.** 위 표의 마지막 열이 메시지 본문입니다. 게임 로그를 읽으러 가지 않게 하는 것이 이 기능의 목적이기 때문입니다.
* 목록에서 항목을 고르면 **그 자리로 격자가 스크롤**됩니다. 경로가 이미 있습니다 — `SetNoteSelection(..., NoteSelectionSource.Search)` 가 격자 밖에서 고른 선택을 그 자리로 스크롤해 줍니다.
* 🔴 한 건이라도 있으면 상태 표시에 **개수**가 보입니다. **저장을 막지는 않습니다** — 작업 중간에는 당연히 짝이 안 맞습니다.

### 언제 다시 도는가

[`NotifyNotesChanged()`](../../bms%20editer/ViewModels/MainWindowViewModel.Editing.cs) **단 한 곳**입니다. 모든 편집 경로가 여기를 지나므로 재계산 자리를 흩어 놓지 않아도 됩니다. 정렬은 그 옆의 `GetSortedNotes()`(`OrderBy(n => n.Measure + n.Position)`)를 **그대로 재사용**합니다 — 새로 만들 필요가 없습니다.

비용은 노트 수에 대해 O(n log n) 이고 실측 규모(340노트)에서는 무시할 수 있습니다. 수만 노트에서 느려지면 "바뀐 레인만 다시 계산"으로 좁히면 됩니다. **그때까지는 전체 재계산이 맞습니다** — 부분 갱신은 캐시가 어긋나는 버그를 부릅니다.

## 8. 표시 (Rendering)

### 홀드 몸통

* 시작·끝의 화면 좌표를 **각각** `ChartTimeline.SecondsAt(measure + position)` 으로 구합니다.
* **마디 단위 선형 보간으로 몸통을 늘리지 마십시오.** BPM 변화(`#xxx03`/`#xxx08`)나 변박(`#xxx02`) 구간을 지나는 홀드의 끝이 어긋납니다. [`bpm_sync_principles.md`](../architecture/bpm_sync_principles.md) 가 같은 이유로 만들어진 규칙입니다.
* 격자는 **세로·가로 보기 둘 다** 있습니다. 몸통도 양쪽에서 그려져야 합니다.
* 고아는 몸통 없이 **점선 캡 + 경고색**으로 표시합니다. "짝이 없다"가 화면에서 바로 보여야 합니다.

### 팔레트 역할 뱃지 — 가장 싸고 먼저 할 것

[`BmsWavItem.DisplayText`](../../bms%20editer/Models/BmsWavItem.cs) 는 이미 `#키: 파일명` 을 보여줍니다. 여기에 역할 뱃지(`▶시작` / `■끝`)만 붙입니다.

> 어떤 프로파일은 **시작이 뒤 글자, 끝이 앞 글자**입니다(`00B`=시작 / `00A`=끝).
> 팔레트에서 번호만 보고 고르면 뒤집힙니다. 가이드가 경고문으로 막고 있는 실수인데,
> **뱃지 하나면 구조적으로 사라집니다.** 페어링 엔진보다 먼저, 거의 공짜로 들어갑니다.

## 9. 기존 편집 기능이 짝을 깨는 자리

검사기가 잡아야 하는 실제 경로입니다. 전부 **지금 있는** 기능입니다.

| 기능 | 어떻게 깨지나 | 검사기가 말할 것 |
|:---|:---|:---|
| [`ReplaceWavKey`](../../bms%20editer/ViewModels/MainWindowViewModel.Editing.cs) | 선택 노트의 키음을 일괄 교체 → 시작이 끝 키음으로 바뀐다 | `OrphanHead` + `OrphanTail` 동시 |
| `CopyNotesByMeasureOffset` | 짝의 **한쪽만** 선택해 복사할 수 있다 | 복사된 쪽이 고아 |
| `MoveSelectedNotes` | 끝을 시작보다 앞으로 밀 수 있다 | `ReversedPair` |
| `DeleteNotes` | 한쪽만 지울 수 있다 | 남은 쪽이 고아 |
| `PlaceNote` | 같은 자리에 찍으면 **기존 노트의 키음을 덮어쓴다** | 덮인 쪽이 고아 |
| 순서 방식(전략 ③)에서 **삽입** | 뒤의 모든 짝이 뒤집힌다 | `ParityBreak` (첫 지점만) |

> [!NOTE]
> 이 표는 "막아야 할 목록"이 아닙니다. **일괄 작업을 그대로 두고, 깨지면 즉시 보이게 하는 것**이 이 설계의 선택입니다.
> 짝을 깨는 편집을 금지하면 작업이 느려지고, 지금 가장 큰 문제가 바로 느린 것입니다.

## 10. 프로파일을 어디에 담고 어떻게 고르나

### 담는 자리 — 단일 exe를 깨지 않는다

[README.md](../../README.md) 는 *"이 exe만 복사하면 실행됩니다"* 를 약속하고, 실제 배포 산출물은 exe 하나입니다. 외부 JSON 폴더만 쓰면 이 약속이 깨집니다 — exe만 복사해 간 사용자는 홀드가 전부 안 잡히는데 이유가 화면에 없습니다.

| 자리 | 쓰는 법 |
|:---|:---|
| `Assets/profiles/*.json` **내장** | csproj에 `<AvaloniaResource Include="Assets\**" />` 가 **이미 있습니다.** 기본 프로파일은 exe 안에 들어가고 단일 exe가 유지됩니다 |
| exe 옆 `profiles/` **덮어쓰기** | 있으면 같은 id의 내장 프로파일을 대체합니다. **리빌드 없이 게임을 추가**할 수 있습니다 |

### 고르는 법 — 반드시 한 번에 하나

여러 프로파일을 동시에 적용하면 **오검출이 확정**입니다. 키음 `02` 는 어떤 게임에서 홀드 시작이지만 다른 게임에서는 그냥 2번 키음입니다.

차트가 자기 프로파일을 들고 다녀야 합니다. 비표준 헤더 선례가 이미 있습니다 — `#BMSEDITER_OFFSET`([파서](../../bms%20editer/Services/BmsParser.cs) · [라이터](../../bms%20editer/Services/BmsWriter.cs)).

```bms
#BMSEDITER_PROFILE deflate
```

* 이 줄이 **없으면 홀드 감지가 전부 꺼집니다.** 일반 BMS는 지금과 완전히 같이 동작합니다(불변식 I-2).
* 게임 모드 쪽 파서는 모르는 헤더를 무시하므로 주입에 영향이 없습니다.

## 11. 단계별 계획과 수용 조건

| 단계 | 내용 | 리스크 | 얻는 것 |
|:---:|:---|:---:|:---|
| **P0** | 팔레트 **역할 뱃지**(§8) + 프로파일 로딩 최소 골격 | 없음 (표시뿐) | 시작/끝을 뒤집어 찍는 실수가 사라진다 |
| **P1** | 전략 ① + 페어링 엔진 + 검사기 + 몸통 렌더 | 낮음 (휴리스틱 0) | **엔진·검사기·렌더 골격 전부.** 프로파일 2종 |
| **P2** | 전략 ② (키워드 표만 다른 프로파일 **2종이 동시에** 들어온다) | 중간 (파일명 휴리스틱) | 파일명 기반 게임 전부 |
| **P3** | 전략 ③ + `ParityBreak` | 높음 (전파가 있다) | **유일하게 실측된 게임.** 40~60분짜리 디버깅 구간 |
| **P4** | 드래그로 홀드 배치(§13) | — | **되돌리기 뒤로 미룬다** |

P0~P3 은 **읽고 보여주기만** 하므로 되돌리기가 없어도 안전합니다. P4만 파일을 바꾸므로 [B-1 되돌리기](../issues/authoring_time.md) 뒤입니다.

> 착수 순서가 "가장 시급한 게임"이 아니라 **"가장 확실한 전략"** 순인 이유: P1 의 전략 ①은 휴리스틱이 0이라
> 엔진·검사기·렌더가 틀렸을 때 **전략 탓인지 엔진 탓인지 헷갈리지 않습니다.** 골격을 여기서 굳히고,
> 불확실한 전략 ②③을 그 위에 얹습니다.

## 12. 미검증 프로파일을 어떻게 다루나

프로파일 중 실제 채보 코퍼스 테스트(`RealGameChartTests.cs`)를 통과한 프로파일(스타트레일, 스타게이저, 건볼트, DEFLATE, UNBEATABLE)은 실측 검증 완료 상태입니다. 신규 게임 추가 등 소스 분석 기반 추정인 경우 미검증 상태로 시작합니다.

> [!WARNING]
> 몸통이 이어져 그려지면 사용자는 결과를 신뢰하게 됩니다.
> 프로파일이 틀렸을 때 **"자신 있게 틀린 몸통"은 "아무것도 안 보임"보다 나쁩니다.**

* 프로파일마다 검증 상태를 값으로 갖습니다: `"verification": "Real"`(실측) / `"Source"`(소스 기반 추정).
* `"Source"` 인 프로파일을 쓰는 동안 상단 툴바에 **"이 프로파일은 실측 검증 전입니다"** 노란색 경고 배너를 띄웁니다.
* [game_profiles.md](game_profiles.md) 의 ✅/⬜ 열이 그 값의 출처입니다. **문서와 코드가 같은 한 곳을 봅니다.**

### 열린 질문 (확인되면 프로파일과 이 문서를 고칩니다)

| # | 질문 | 확인 방법 |
|:--:|:---|:---|
| **Q1** | 전략 ③에서 홀드와 샌드백의 출현 수열이 **정말 따로** 세어지는가? 한 수열이면 서로 닫아 버린다 | 한 채널에 홀드·샌드백을 번갈아 넣고 게임 로그 확인 |
| **Q2** | 전략 ③의 숫자 위치가 **몇 번째 자리**인가 (한 자리 단위 vs 두 자리 묶음) | 예시 파일명과 실제 스폰 결과 대조 |
| **Q3** | N:M 끝 키음(아크)에서 **어느 시작이 어느 끝과** 짝지어지는가 — `Fifo` 인가 `Lifo` 인가 | 중첩 아크를 하나 만들어 확인 |
| **Q4** | 길이 0 홀드를 게임이 어떻게 처리하는가 (스폰 · 무시 · 크래시) | 같은 자리에 시작·끝을 찍고 확인 |

## 13. 드래그로 홀드 배치 — 입력 충돌을 먼저 풀어야 한다

"시작에서 끝까지 그으면 짝 2개가 자동 생성" 은 짝이 구조적으로 안 깨지게 하는 가장 좋은 방법이지만, **지금 입력과 정면으로 충돌합니다.**

* 편집 모드 좌클릭은 **누른 순간 즉시 배치**합니다([`NoteGridControl`](../../bms%20editer/Views/Controls/NoteGridControl.cs) `OnPointerPressed`).
* Ctrl/Shift + 드래그는 **범위 선택에 이미 할당**되어 있습니다.

| 선택지 | 장점 | 단점 |
|:---|:---|:---|
| (a) 별도 홀드 도구 토글 | 기존 감각을 건드리지 않는다 | 토글 왕복이 늘어난다 |
| **(b) "시작 찍고 → 끝 찍기" 2클릭** | 새 입력 규칙이 없다. 구현이 가장 가볍다 | 중간 상태(시작만 찍힌)를 보여줘야 한다 |
| (c) 편집 모드 좌클릭을 press-drag-release 로 | 가장 직관적 | **단타 배치 감각이 바뀐다.** 340개를 찍는 작업에서 이건 큰 변화다 |

현재 기울어져 있는 쪽은 **(b)** 입니다 — 기존 입력을 전혀 바꾸지 않고, 중간 상태는 P1의 고아 표시(점선 캡)를 그대로 씁니다. 확정은 P3 이후입니다.
