# 🎮 게임 프로파일 — 게임별 값 한 곳

> [!NOTE]
> **게임마다 다른 값만 모아 둔 단일 표입니다.** 어떤 레인을 쓰는지, 홀드를 무엇으로 판별하는지,
> 어디까지 확인했는지를 여기 한 곳에서만 관리합니다.
>
> 짝을 맞추는 **규칙과 알고리즘**은 게임과 무관하므로 [🔗 홀드 짝 맞추기 사양](hold_pairing_spec.md) 에 있습니다.
> 작성 **시간**과 개선 후보는 [⏱️ authoring_time.md](../issues/authoring_time.md) 에 있습니다.

> [!IMPORTANT]
> **진실은 프로파일 JSON(`bms editer/Profiles/*.json`)입니다.** 이 표는 그 파일을 사람이 읽기 좋게 옮긴 것입니다.
> 값을 고칠 때는 JSON 을 먼저 고치고 이 표를 맞추십시오. 둘이 다르면 JSON 이 맞습니다.
>
> 게임을 추가할 때 손볼 곳은 세 군데입니다. 아래 표에 한 줄 + 프로파일 JSON 하나 + `guides/` 에 가이드 하나.
> 다른 문서들은 게임 표를 따로 들지 않고 이 파일로 링크합니다.

### 검증 상태 — JSON 의 `verification` 값

| 표시 | JSON 값 | 뜻 | 화면 |
|:---:|:---|:---|:---|
| ✅ 플레이 확인 | `Playtested` | 실제로 채보를 만들어 게임에서 확인했다 | "실제 채보를 만들어 게임에서 확인한 규칙입니다." |
| 🔶 코드 확인 | `Source` | 게임 모드의 파서 소스로 규칙을 확인했다. 플레이로는 아직 확인하지 않았다 | "게임 모드 코드로 확인한 규칙입니다. 실제 플레이로는 아직 확인 전입니다." |
| ⚠️ 가정 | `Assumed` | 짝 규칙을 게임 코드로 확인하지 못했다. 모양만 흉내 낸 것이다 | **주황색** 경고: "화면의 홀드 몸통을 그대로 믿지 마십시오." |

> [!NOTE]
> **뮤즈 대시가 유일한 `Playtested` 인 이유:** 실제로 340노트 채보를 약 4시간 들여 만들어 본 게임이 뮤즈 대시뿐입니다.
> 바로 그 작업이 너무 오래 걸려서 **공식 채보 작성 대상에서는 뺐습니다**([authoring_time.md](../issues/authoring_time.md)).
> 프로파일은 exe 에 그대로 들어 있고 드롭다운에서 고를 수 있습니다. 짝 검사기(`ParityBreak`)도 동작합니다.

## 🔧 2. 프로파일별 파라미터

JSON 에 들어 있는 값입니다. 판별 방식과 짝 정책의 뜻은 [hold_pairing_spec.md §2·§5](hold_pairing_spec.md) 를 보십시오.

### 스타트레일 (`startrail`) — KeyValue

| `kind` | 채널 | 시작 키 | 끝 키 | 정책 | 범위(`scope`) |
|:---|:---|:---:|:---:|:---|:---|
| `Hold` | `16` `11`~`15` `18` | `02` | `03` | `ReplacePending` | `Channel` — 레인마다 따로 |
| `Gate` | `16` `11`~`15` `18` | `04` | `05` | `ReplacePending` | `AllChannels` — 채널을 가리지 않고 한 줄로 |

> 게임 파서는 레인마다 **대기 칸이 하나뿐**이라, 끝이 오기 전에 시작이 또 오면 앞 시작을 버립니다(`ReplacedHead` 진단).
> 게이트(키음 값 `04`/`05`)는 어느 채널에 찍든 게임 레인 9번 하나로 모여 짝지어지므로 `AllChannels` 입니다.
> 채널이 다른 짝은 격자에 몸통 대신 **연결선**으로 그립니다.
>
> 가이드의 채널 `#xxx04`/`#xxx05`(게이트 레인 연출)는 편집 대상 밖이라 원문 보존으로만 통과합니다.
> 편집 레인에 찍는 **키음 값** `04`/`05` 와 다른 층입니다.

### 스타게이저 (`stargazer`) — FileNameKeyword

| 항목 | 값 |
|:---|:---|
| 필수 키워드 | **`hold`** — 이게 없는 파일명은 전부 일반 단노트 |
| 시작 키워드 | `시작` `start` |
| 끝 키워드 | `끝` `end` |
| `tailFirst` | **`false`** — 모드가 시작 키워드를 먼저 본다 |
| 정책 | `NearestUnconsumedTail` (**가정**) |

> [!WARNING]
> 모드는 노트마다 `StartPoint`/`EndPoint` 표식만 넘기고 **짝은 게임 엔진이 맺습니다.** 그 규칙은 확인되지 않았습니다.
> 그래서 이 프로파일만 `Assumed` 이고, 화면에 주황색 경고가 뜹니다.
>
> DEFLATE 와 같은 판별 방식이지만 **필수 키워드가 있다는 점이 다릅니다.** `synth_start.wav` 는 두 게임 어디서도 홀드가 아닙니다.

### 건볼트 (`gunvolt`) — KeyValue (N:M)

| `kind` | 시작 키 | 끝 키 | 정책 |
|:---|:---|:---|:---|
| `Hold` | `02` | `19` | `NearestTailShared` — 끝 노트를 **소비하지 않는다** |
| `Fairy` | `11` `12` `13` `14` `15` `16` `17` `18` (8방향) | `1A` `1B` | `FifoQueue` — 가장 오래 기다린 시작과 짝 |

> [!IMPORTANT]
> * 홀드는 끝 노트를 소비하지 않아서 **시작 여러 개가 끝 하나를 같이 쓸 수 있습니다.** 게임은 정상으로 받지만,
>   의도한 배치인지 확인하라는 뜻으로 `SharedTail` 주의를 띄웁니다.
> * 페어리는 시작 8종 ↔ 끝 2종의 N:M 입니다. 시작을 줄 세우고, 같은 자리면 시작이 먼저입니다.
>   끝이 시작보다 앞서지 않으면 게임 코드처럼 **둘 다 버립니다**(둘 다 고아).
> * 8방향 플릭(`03`~`0A`)은 짝이 없는 단발이라 대상이 아닙니다. 채널 `13` 은 노트 채널이 아닙니다.

### DEFLATE (`deflate`) — FileNameKeyword

| 항목 | 값 |
|:---|:---|
| 채널 | `16` `11` `12` `13` `14` |
| 시작 키워드 | `홀드 시작` `홀드시작` `hold start` `holdstart` `hold_start` `ln start` `lnstart` |
| 끝 키워드 | `홀드 끝` `홀드끝` `hold end` `holdend` `hold_end` `ln end` `lnend` |
| 필수 키워드 | 없음 |
| `tailFirst` | **`true`** — 양쪽을 다 담은 파일명은 끝 |
| 정책 | `NearestUnconsumedTail` — 시작마다 뒤에 있는 아직 안 쓴 끝 중 가장 가까운 것 |

> [!CAUTION]
> **홀드 쌍 키음이 번호 순서와 반대입니다.** `00B`=시작 / `00A`=끝, `00D`=시작 / `00C`=끝 …
> 팔레트에서 번호만 보고 고르면 뒤집히기 쉽습니다. 팔레트 역할 뱃지는 **아직 없습니다**([spec §8](hold_pairing_spec.md)).
> 대신 뒤집어 찍으면 격자에 몸통이 안 생기고 고아 경고(주황 점선)가 뜨므로 그 자리에서 알 수 있습니다.
>
> 레인 `15`·`18` 에 찍은 노트는 게임에서 **경고 없이 조용히 사라집니다.** 드롭 레인(`14`)에는 홀드 쌍이 없습니다.

### UNBEATABLE (`unbeatable`) — FileNameBase + 출현 순서

| 항목 | 값 |
|:---|:---|
| 채널 | `16` `11` `12` `13` `14` `15` |
| 종류(`kind`) | `Hold` · `Double` · `Spam` — 파일명 기본명으로 정한다 |
| 떼어낼 접미사 | ` end` (공백 포함) — 떼어낸 뒤 기본명을 비교한다 |
| 정책 | `Alternate` — 같은 레인·같은 종류가 나온 순서로 홀수=시작, 짝수=끝 |

> ` end` 표식 자체는 게임이 짝을 정하는 데 쓰지 않습니다. 에디터는 표식과 순서가 **처음 어긋난 자리**를
> `ParityBreak` 로 알리는 데만 씁니다. 채널 `18` 은 노트가 아니라 카메라/방향 전환 연출입니다.

### 뮤즈 대시 (`muse_dash`) — FileNameUid + 출현 순서 · **지원 제외**

> [!WARNING]
> 6자리 UID 체계와 출현 순서 전파 때문에 작성 시간이 너무 길어(340노트에 약 4시간) **공식 채보 작성 대상에서 제외**했습니다.
> 아래는 exe 에 들어 있는 프로파일의 값입니다.

| 항목 | 값 |
|:---|:---|
| UID | 파일명 앞 6자리 숫자 (`^([0-9]{6})`) |
| 앞 4자리(우선) | `0002`=하트 · `0003`=스코어 · `0004`=씬 전환 → 짝 대상 아님 |
| 타입 자리 | 0부터 센 `offset 2`, `length 2` — `02`=홀드, `04`=샌드백, `03`/`09`=장애물, `17`=유령 |
| 이름 추정 | UID 로 안 정해질 때만 `heart`·`score`·`sandbag`·`hold` 등 키워드로 |
| 정책 | `Alternate` — `Hold` 와 `Sandbag` 은 **수열을 따로** 센다 (게임 코드 확인) |

> [!CAUTION]
> **출현 순서 방식에만 전파가 있습니다.** 수열 중간에 홀드를 끼워 넣으면 **그 뒤 전부가 뒤집힙니다.**
> 검사기는 **처음 어긋난 자리**만 `ParityBreak` 로 지목합니다. 파일명 끝 `_dt[초]` 는 오프셋 델타라서
> 이 게임에서는 접미사를 키워드로 쓰면 안 됩니다.

## 🚫 3. 모든 프로파일에 공통인 것

* **편집 대상 채널은 `16,11,12,13,14,15,18` 뿐입니다**([`BmsParser`](../../bms%20editer/Services/BmsParser.cs)). 프로파일의 채널 목록은 이 중 **어디를 보는지**를 좁히는 것이고, 넓히지는 못합니다.
* **표준 LN 채널 `51~59` 와 `#LNOBJ` 는 어느 프로파일도 쓰지 않습니다.** 원문 보존으로 통과만 합니다.
* **프로파일이 정해지지 않으면 홀드 감지가 전부 꺼집니다.** 일반 BMS 는 지금과 똑같이 동작합니다.
* 프로파일은 이 순서로 정해집니다([spec §10](hold_pairing_spec.md)).
  1. 파일의 `#BMSEDITER_PROFILE <id>` — 사용자가 드롭다운에서 고르면 저장할 때 적힙니다.
  2. 없으면 차트 경로의 폴더 이름(`pathHints`)으로 추정 — **화면에만 쓰고 파일에는 적지 않습니다.**
* 조건 블록(`#RANDOM`/`#IF`)의 갈래끼리는 절대 짝짓지 않습니다.

## ➕ 4. 게임을 추가하는 절차

1. 게임 모드의 파서 소스를 읽고 `guides/` 에 **가이드 문서** 하나를 씁니다.
2. `bms editer/Profiles/<id>.json` 을 추가합니다. **코드는 고치지 않습니다.** 판별 방식(`role.type`)과
   짝 정책(`policy`)은 이미 있는 것 중에서 고릅니다. 맞는 것이 없으면 [spec §2·§5](hold_pairing_spec.md) 에 먼저 적고 코드에 추가합니다.
   `FileNameUid`/`FileNameBase` 는 `Alternate` 와만, 나머지는 `Alternate` 가 아닌 정책과만 짝이 맞습니다(읽을 때 검사합니다).
3. `verification` 은 게임 코드로 확인했으면 `Source`, 아니면 `Assumed` 로 시작합니다.
4. **이 문서 §1 표에 한 줄**, §2 에 파라미터 절을 추가합니다.
5. 실제 차트 대조를 넣으려면 테스트의 `GameOracles` 에 게임 코드를 옮기고 `GameChartCorpus` 에 게임 폴더를 적습니다.
6. 실제로 채보를 만들어 게임에서 확인하면 `Playtested` 로 올립니다.

> exe 옆에 `profiles\` 폴더를 두고 같은 id 의 JSON 을 넣으면 내장 프로파일을 덮어씁니다. 리빌드 없이 시험해 볼 수 있습니다.
