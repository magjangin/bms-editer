## 🔧 A. 조건 블록 지원 (해결 완료 ✅)

* **처음 문제**: 조건 블록(`#RANDOM`/`#IF`/`#SWITCH`) 안의 건반 줄이 평범한 노트로 읽혀 저장 시 한 줄로 합쳐지거나 헤더 위치로 끌려 올라갔습니다.
* **1차 해결(`7ec07f1`)**: `BmsNote`·`BmsRawLine` 에 갈래(`BranchId`)와 원본 줄 순서를 추적하고, 라이터가 갈래별로 줄을 나눠 씁니다.
* **2026-09-22 점검에서 찾은 🔴 버그**: 라이터가 제어 줄(`#IF` 등)을 "바로 앞 데이터 줄의 마디"에 매달아 **마디 순으로 다시 정렬**했습니다. 그래서
  - 블록 뒤에 온 무조건 줄(같은 마디의 BGM·건반)이 `#IF 1` 안으로 끌려 들어가 1번 갈래에서만 울렸고,
  - 블록을 파일 끝에 몰아 둔 차트(블록 안 마디 < 앞 줄의 마디)는 **`#IF` 가 닫히지 않은 파일**이 되었습니다.
  - 파서는 `#CASE`·`#DEF` 마다 갈래를 쌓기만 하고 닫지 않아서 `#ENDSW` 뒤 노트가 마지막 CASE 로 읽혔습니다.
* **2차 해결(`78f2eb3`)**: 파서와 라이터가 같은 상태 기계([`ConditionalBlocks`](../../bms%20editer/Services/ConditionalBlocks.cs))를 씁니다.
  블록 밖의 줄은 마디 순으로, **블록 영역 안의 줄(제어 줄·원문 줄·주석·갈래 노트)은 원래 줄 순서 그대로** 뒤에 붙입니다.
  `#ENDRANDOM` 이 없으면 블록이 파일 끝까지 이어진 것으로 봅니다. 회귀 테스트 5건(`SaveIntegrityTests`).
* 남은 것: [조건 블록 안의 헤더](#-조건-블록-안의-헤더가-블록-밖으로-올라간다).

## 🔊 B. 키음 다중 채널 믹싱 재생 (해결 완료 ✅)

* **이전 문제**: Win32 `PlaySound(SND_ASYNC)`를 사용하여 단일 채널로 재생되었기 때문에, 화음이나 빠른 연타 시 앞선 소리가 끊기고 채보 귀 검수가 불가능했습니다.
* **해결 구조**:
  - `WavDecoder`를 통해 WAV (8/16/24/32bit PCM, IEEE Float, `WAVE_FORMAT_EXTENSIBLE`) 및 OGG 파일을 44100Hz 16-bit Stereo PCM으로 백그라운드 사전 디코딩하여 메모리에 캐싱.
  - Win32 `waveOut` 네이티브 헤더(`WAVEHDR`) 포인터를 직접 제어하는 `KeySoundPlayer` 스트리밍 믹서를 구축하여 포화 가산(Saturation Clamping)으로 실시간 다중 채널(폴리포닉) 믹싱을 완벽 지원합니다.

## 🟡 키음이 배경음보다 늦게 울릴 수 있다

[`KeySoundPlayer`](../../bms%20editer/Services/KeySoundPlayer.cs) 는 40ms 버퍼 3개를 앞서 채워 두고 재생합니다.
새 키음은 **이미 대기열에 들어간 버퍼들 뒤**에 섞이므로 구조상 최대 약 80~120ms 늦게 나옵니다.
울릴 노트를 고르는 재생 타이머도 33ms 간격이라 그만큼 더 흔들립니다. 배경음(`OggAudioPlayer`)은 곡 전체를 한 버퍼로 넘기고
장치가 실제로 재생한 위치로 커서를 잡으므로 이 지연이 없습니다.

**확인 방법**: 클릭 트랙 음원에 같은 박마다 키음을 찍고 1.0x 로 재생해, 키음이 박보다 늦게 들리는지 들어 봅니다(녹음해서 파형으로 재면 확실합니다).

**고칠 방향**: 버퍼를 줄이거나(끊김과 맞바꿈), 대기 중인 버퍼 길이만큼 키음을 **미리** 예약해 두는 방식(재생 위치 + 지연만큼 앞의 노트를 미리 믹서에 넣기).
박자 가이드에는 "판단은 배속을 낮춘 상태에서" 라고 적어 두었습니다([beat_sync_workflow.md](../guides/beat_sync_workflow.md)).

## 🟡 조건 블록 안의 헤더가 블록 밖으로 올라간다

파서가 1단계에서 읽어 가는 헤더(`#TITLE`·`#BPM`·`#WAV` 등, `IsConsumedHeader`)는 저장할 때 에디터가 헤더 블록에 새로 씁니다.
그래서 `#IF` 안에 있던 `#WAV01 alt.wav` 나 `#BPM 150` 은 저장하면 **갈래 밖(무조건)** 으로 옮겨지고, 같은 키가 두 번이면 마지막 값만 남습니다.
에디터가 모르는 헤더(`#BMP`·`#STOP`·`#BPMxx` 등)와 주석은 블록 안에 그대로 남습니다.

**고칠 방향**: 블록 영역 안의 헤더는 원문 그대로 블록에 남기고, 헤더 블록에는 블록 밖에서 읽은 값만 씁니다.
`WavTable` 이 갈래를 모르므로 재생·짝 맞추기가 어느 갈래의 `#WAV` 를 쓸지도 함께 정해야 합니다.

## 🟡 25-2. 비디오가 ScrollViewer 밖으로 삐져나온다

[VideoPreviewControl.cs](../../bms%20editer/Views/Controls/VideoPreviewControl.cs) 는
네이티브 창(HWND)이라 Avalonia 의 `ClipToBounds` 가 먹지 않습니다.
`_controller.Bounds` 를 좌표만 보고 잡는데, 오른쪽 패널을 스크롤하면 원점이 패널 밖으로 나갑니다.
툴바 위로 비디오가 삐져나올 수 있습니다.

**확인 방법**: 비디오를 띄운 채 오른쪽 패널을 위아래로 스크롤합니다.

**고칠 방향**: 부모의 보이는 영역과 교차한 사각형으로 `Bounds` 를 잘라 넣고,
완전히 벗어나면 `IsVisible = false` 로 둡니다.

## 🎛️ 되살린 것: 집계에서 키음으로 노트 찾기

한때 통계 창에 있었다가 **걷어냈던** 기능입니다. 이번에 **🎛️ 컨트롤 패널**이라는 별도 창으로 다시 만들어 넣었습니다.
(`ControlPanelViewModel` · `ControlPanelWindow`)

### 왜 접었었나

만드는 동안 세 번 헛돌았고, 매번 원인이 달랐습니다.

| 시도 | 무엇이 문제였나 |
|------|----------------|
| 1 | 명령을 `{Binding $parent[ItemsControl].((vm:NoteStatsViewModel)DataContext).…}` 로 끌어왔는데, 컴파일된 바인딩에서 **조용히 실패**했습니다. `Command` 가 null 인 버튼이라 눌러도 아무 일이 없었고, 빌드도 예외도 멀쩡했습니다 |
| 2 | 버튼 스타일(`Background`·`BorderBrush`)이 **Fluent 테마의 Button 템플릿에 가려** 화면에 안 나타났습니다. 누를 수 있다는 표시가 없으니 누를 생각을 할 이유도 없었습니다 |
| 3 | `ListBox` 로 바꿔 동작은 했지만, 고른 노트가 화면 밖이면 여전히 눌렸는지 알기 어려웠습니다. 격자를 그리로 스크롤하고 안내문을 붙이며 덧대다 보니 통계 창의 몫이 아닌 일이 늘었습니다 |

### 이번에는 무엇을 다르게 했나

| 예전에 걸린 것 | 이번 방식 |
|----------------|-----------|
| 목록 항목 안에서 조상 바인딩으로 명령을 끌어옴 | **목록 항목에는 명령을 걸지 않습니다.** 고른 줄은 `SelectedItem` 으로만 받고(`SelectedLaneStat`·`SelectedWavStat`), 누르는 것은 전부 목록 **밖**의 버튼입니다. 창의 `DataContext` 가 곧 뷰모델이라 바인딩이 한 칸도 건너뛰지 않습니다 |
| 버튼이 테마 템플릿에 가려 안 보임 | 항목 안에 버튼을 두지 않으니 가려질 자리 자체가 없습니다. 고른 줄은 검색 창·팔레트와 같은 파랑(`#3B6FD4`)으로 강조합니다 |
| 고른 노트가 화면 밖이면 눌렸는지 알 수 없음 | 선택을 `NoteSelectionSource.Search` 로 알려 **그 자리로 스크롤**시키고(`ScrollToRatioRequested`), 결과를 창 아래 한 줄(`StatusMessage`)로 말해 줍니다 |
| 뷰모델은 멀쩡한데 화면에서 끊어짐 | 창을 실제로 띄워 **작업 버튼 6개에 `Command` 가 붙어 있는지** 확인하는 테스트를 넣었습니다(`WindowSmokeTests`) |

검색 창과 역할이 겹치지 않느냐는 판단은 이렇게 갈랐습니다.
**"이 번호가 몇 개 있나"에서 곧장 손대는 것**은 컨트롤 패널이 맡고,
**"조건을 조합해 찾는 것"**(마디 범위 · 노트 종류 · 여러 레인)은 그대로 검색 창의 몫입니다.
컨트롤 패널의 일괄 작업은 언제나 **고른 줄 하나**를 대상으로 합니다.

> 📊 통계 창은 **보기 전용으로 남겨 두었습니다.** 숫자만 볼 때 잘못 눌러 수백 개가 바뀌는 일이 없고,
> 집계 규칙은 `NoteStatsViewModel` 한 곳뿐이라 두 창의 숫자가 갈라지지 않습니다.

> 되돌리기가 아직 없으므로([C](#-c-undo--redo)), 컨트롤 패널의 **일괄 삭제만은 먼저 물어봅니다.**
> 확인 창을 띄울 길이 없으면(`ConfirmAsync` 가 없으면) 아무것도 지우지 않습니다.

### 🅿️ 나중에 고려: 패널 맨 위의 열(레인) 선택 칸

"레인별 노트 개수 + [레인 노트 선택]" 칸은 **모양을 다시 볼 자리로 남겨 둡니다.**
지금은 한 번에 레인 하나만 고를 수 있어서, 여러 열을 묶어 고르는 일은 검색 창의 열 토글이 더 낫습니다.
게다가 편집 대상 레인이 `16,11,12,13,14,15,18` 로 고정돼 있어 열 개수 자체가 바뀔 여지가 있습니다.
**어떤 모양이어야 하는지는 그때 정합니다.** 그 전까지는 지금 형태로 둡니다.

같이 볼 것: 다중 선택(여러 레인 한꺼번에), 1P/2P 묶음 표시, 검색 창의 열 조건과 역할 나누기.
