## 🔧 A. 조건 블록 지원 (해결 완료 ✅)

* **처음 문제**: 조건 블록(`#RANDOM`/`#IF`/`#SWITCH`) 안의 건반 줄이 평범한 노트로 읽혀 저장 시 한 줄로 합쳐지거나 헤더 위치로 끌려 올라갔습니다.
* **1차 해결(`7ec07f1`)**: `BmsNote`·`BmsRawLine` 에 갈래(`BranchId`)와 원본 줄 순서를 추적하고, 라이터가 갈래별로 줄을 나눠 씁니다.
* **2026-09-22 점검에서 찾은 것 (미해결)**: 라이터가 제어 줄(`#IF` 등)을 "바로 앞 데이터 줄의 마디"에 매달아 다른 줄과 함께 **마디 순으로 다시 정렬**합니다.
  줄이 마디 순으로 적힌 단순한 차트는 괜찮지만, 아래 배치에서는 저장 결과의 줄 순서가 섞입니다(임시 프로그램으로 저장 결과를 확인했습니다).
  - 블록 뒤에 같은 마디의 무조건 줄(BGM·건반)이 있으면, 그 줄이 `#IF 1` 안으로 들어갑니다.
  - 블록을 파일 끝에 몰아 둔 차트(블록 안 마디 < 블록 앞 줄의 마디)는 `#IF` 가 닫히지 않은 순서로 저장됩니다.
  - 블록 안의 주석과 모르는 헤더(`#BMP` 등)는 헤더 영역으로 옮겨집니다.
  → 자세한 내용과 확인 방법: [점검 목록 1·2번](#-2026-09-22-점검에서-찾은-것-확인-필요)

## 🔊 B. 키음 다중 채널 믹싱 재생 (해결 완료 ✅)

* **이전 문제**: Win32 `PlaySound(SND_ASYNC)`를 사용하여 단일 채널로 재생되었기 때문에, 화음이나 빠른 연타 시 앞선 소리가 끊기고 채보 귀 검수가 불가능했습니다.
* **해결 구조**:
  - `WavDecoder`를 통해 WAV (8/16/24/32bit PCM, IEEE Float, `WAVE_FORMAT_EXTENSIBLE`) 및 OGG 파일을 44100Hz 16-bit Stereo PCM으로 백그라운드 사전 디코딩하여 메모리에 캐싱.
  - Win32 `waveOut` 네이티브 헤더(`WAVEHDR`) 포인터를 직접 제어하는 `KeySoundPlayer` 스트리밍 믹서를 구축하여 포화 가산(Saturation Clamping)으로 실시간 다중 채널(폴리포닉) 믹싱을 완벽 지원합니다.

## ↩️ C. Undo / Redo

가장 큰 빈 자리입니다. 저장은 이제 안전하고(원자적 저장 + `.bak` + [저장 이력·자동 저장](#-g-안전장치-해결-완료-)), **편집 자체는 되돌릴 수 없습니다.**
지금은 잘못 지운 것을 되찾으려면 자동 저장 폴더에서 그 전 스냅숏을 찾아 곡 폴더에 복사해 넣어야 합니다.

특히 위험한 조합:
* 검색창의 [삭제]는 한 번에 수백 개를 지웁니다
* [번호 일괄 변경]도 마찬가지입니다
* 둘 다 20개 이상이면 먼저 묻지만(`aa685e4`), 한 번 확인하면 되돌릴 수 없습니다

**고칠 방향**: 노트 편집이 전부 `MainWindowViewModel` 의 몇 개 메서드를 지나가므로
(`PlaceNote`·`RemoveNote`·`DeleteNotes`·`MoveSelectedNotes`·`ReplaceWavKey`·`CopyNotesByMeasureOffset`),
그 자리에 명령 기록을 끼우면 됩니다.

## 📉 D. 렌더링 비용

`NoteGridControl` · `OggWaveformControl` 은 매 프레임 타임라인 **전체**를 그립니다.
5분·BPM 150·16분할이면 격자선만 약 3,000개 × 2컨트롤, 192분할이면 약 36,000개 × 2.
재생 타이머가 33ms마다 위치를 바꾸므로 초당 30번 반복됩니다.

보이는 구간만 그리는 뷰포트 컬링을 넣었다가(`8b44887`) 격자선·노트가 빠지는 렌더 무결성 문제가 생겨 **되돌렸습니다**(`10e1937`).
지금은 전체를 그리고, 화면 밖은 Skia 캔버스 클리핑이 잘라냅니다. 느려지는 실사용 사례가 나오면 다시 봅니다.

## 🛟 G. 안전장치 (해결 완료 ✅)

| 폴더 | 무엇이 있나 |
|------|-------------|
| `recovery\snapshots\<곡폴더>_<파일명>_<해시>\` | 문서마다 한 폴더. `…_auto.bms` 는 자동 저장본, `…_before-save.bms` 는 [저장]이 덮어쓰기 직전의 파일. 종류별로 최근 **10벌**만 남고, 한 달 넘게 안 쓴 문서 폴더는 지웁니다. 옆의 `.json` 은 원래 경로·인코딩 기록입니다 |

| `logs\` | 오류 기록 `error-*.log`. 최근 30건만 남깁니다 |

**어떻게 동작하나**

| 상황 | 동작 |
|------|------|
| 편집 중 | 저장 안 된 변경이 있으면 **2분마다** 자동 저장합니다. 그 사이 바뀐 게 없으면 새로 쓰지 않습니다 |
| [저장] | 덮어쓰기 직전의 파일을 저장 이력으로 옮겨 둡니다(곡 폴더의 `.bak` 은 여전히 한 벌). 바로 앞 이력과 똑같으면 또 만들지 않습니다 |
| 예상하지 못한 예외 (UI 스레드) | 앱이 꺼지지 않습니다. 재생을 멈추고, **그 자리에서 비상 저장**하고, 오류 기록을 남긴 뒤 "오류" 창에서 [계속 작업]/[끄기]를 묻습니다. [끄기]는 저장 안 된 변경이 있으면 늘 쓰던 "저장하고 닫을까요?" 로 이어집니다. 창이 떠 있는 동안 또 나면 기록만 남깁니다 |
| 앱이 죽었다 (강제 종료·전원 등) | 다음 실행 때 **"작업 복구"** 창이 뜹니다. [복구] 는 마지막 자동 저장본을 원래 자리의 문서로 되살리고(음원·영상도 다시 붙임) "저장 안 됨(`*`)" 상태로 둡니다. 원래 파일은 [저장]을 눌러야 바뀝니다. [복구 안 함] 은 묻지 않게 하고(자동 저장본은 남음), [취소] 는 다음 실행 때 다시 묻습니다 |
| 저장 안 된 작업 없이 죽었다 | 묻지 않고 세션 파일만 치웁니다 |
| 창 두 개 | 서로의 세션을 "죽었다"고 보지 않습니다(프로세스 번호와 시작 시각으로 가립니다) |

* 이력 스냅숏을 고르는 화면은 없습니다. 원하는 `.bms` 를 **곡 폴더에 복사해 넣고** 이름을 바꿔 열면 됩니다. `#WAV` 경로가 원래 곡 폴더 기준으로 적혀 있어 그대로 열립니다.
* 제목 없는(한 번도 저장 안 한) 문서도 자동 저장·복구하지만, 되살린 뒤 [저장]하면 저장 위치를 새로 묻습니다.

## 🟡 키음이 배경음보다 늦게 울릴 수 있다

[`KeySoundPlayer`](../../bms%20editer/Services/KeySoundPlayer.cs) 는 40ms 버퍼 3개를 앞서 채워 두고 재생합니다.
새 키음은 **이미 대기열에 들어간 버퍼들 뒤**에 섞이므로 구조상 최대 약 80~120ms 늦게 나옵니다.
울릴 노트를 고르는 재생 타이머도 33ms 간격이라 그만큼 더 흔들립니다. 배경음(`OggAudioPlayer`)은 곡 전체를 한 버퍼로 넘기고
장치가 실제로 재생한 위치로 커서를 잡으므로 이 지연이 없습니다.

게다가 믹서는 약 120ms(빈 버퍼 3개) 조용하면 장치를 **닫고**, 다음 키음 때 다시 엽니다.
그래서 늦는 정도가 **구간마다 다릅니다.** 빽빽한 구간은 버퍼 대기열만큼, 듬성한 구간은 장치를 여는 시간만큼 늦습니다 → [P-9](#-재생할-때-걸리는-것-2026-09-24-점검).

**확인 방법**: 클릭 트랙 음원에 같은 박마다 키음을 찍고 1.0x 로 재생해, 키음이 박보다 늦게 들리는지 들어 봅니다(녹음해서 파형으로 재면 확실합니다).

**고칠 방향**: 버퍼를 줄이거나(끊김과 맞바꿈), 대기 중인 버퍼 길이만큼 키음을 **미리** 예약해 두는 방식(재생 위치 + 지연만큼 앞의 노트를 미리 믹서에 넣기).
박자 가이드에는 "판단은 배속을 낮춘 상태에서" 라고 적어 두었습니다([beat_sync_workflow.md](../guides/beat_sync_workflow.md)).

> 집계 규칙은 `NoteStatsViewModel` 한 곳뿐이라 두 창의 숫자가 갈라지지 않습니다.

> 되돌리기가 아직 없으므로([C](#-c-undo--redo)), 컨트롤 패널의 **일괄 삭제는 늘 먼저 물어봅니다.**
> (검색 창의 [삭제]·[번호 일괄 변경]은 20개 이상일 때만 묻습니다 — S-5, `aa685e4`)
> 확인 창을 띄울 길이 없으면(`ConfirmAsync` 가 없으면) 아무것도 지우지 않습니다.

### 🅿️ 나중에 고려: 패널 맨 위의 열(레인) 선택 칸

"레인별 노트 개수 + [레인 노트 선택]" 칸은 **모양을 다시 볼 자리로 남겨 둡니다.**
지금은 한 번에 레인 하나만 고를 수 있어서, 여러 열을 묶어 고르는 일은 검색 창의 열 토글이 더 낫습니다.
게다가 편집 대상 레인이 `16,11,12,13,14,15,18` 로 고정돼 있어 열 개수 자체가 바뀔 여지가 있습니다.
**어떤 모양이어야 하는지는 그때 정합니다.** 그 전까지는 지금 형태로 둡니다.

같이 볼 것: 다중 선택(여러 레인 한꺼번에), 1P/2P 묶음 표시, 검색 창의 열 조건과 역할 나누기.

## 🚫 확인해 보니 문제가 아니었던 것

점검 중 의심했으나 실제로 돌려 보니 정상이었던 것입니다. 같은 의심을 다시 하지 않도록 남깁니다.

| 의심한 것 | 결과 |
|-----------|------|
| `#PLAYER` 왕복이 한 칸씩 밀리지 않는가 (파일은 1/2/3, 콤보박스는 0부터) | **정상.** `PullHeaderFromChart` 의 `Player - 1` 과 `BmsWriter` 의 `player + 1` 이 짝을 이룹니다. 1→0→1, 2→1→2, 3→2→3 으로 세 값 모두 제자리로 돌아옵니다 |
| 데이터 줄 길이가 청크 크기로 안 나누어떨어지면 뒤가 잘리는가 | **잘리는 것은 맞지만** 규격을 벗어난 입력에서만 나옵니다(예: 9자 데이터 → 4개만 읽고 마지막 1자 버림). 우선순위가 낮습니다 |
