# ⏱️ 채보 작성 시간 — 경고와 개선 과제

> [!NOTE]
> **v0.1.4 에서 들어간 것**: 작성 시간의 절반 이상을 먹던 "맞게 찍었는지 확인하는 시간"을 줄이려고
> **게임 프로파일 기반 홀드 짝 자동 인식 · 몸통 표시 · 짝 검사기**를 넣었습니다.
> 다만 그 뒤로 채보를 처음부터 다시 만들어 시간을 잰 기록은 **아직 없습니다.** 얼마나 줄었는지는 다음 실측으로 확인합니다.
> (※ 340노트에 4시간이 걸린 *뮤즈 대시*는 작성 난이도 때문에 공식 지원에서 제외했습니다.)

이 문서를 남기는 이유는 하나입니다. **"만들 수는 있다"와 "쓸 만하다"는 다릅니다.**
가이드만 읽으면 앞의 것만 보이고, 뒤의 것은 실제로 4시간을 써 본 뒤에야 알게 됩니다.
그 사실을 가이드 옆에 붙여 둡니다.

## 📊 실측 기록

실제로 채보를 만들며 시간을 잰 기록입니다.

| 날짜 | 게임 | 규모 | 걸린 시간 | 비고 |
|:---|:---|:---|:---|:---|
| 2026-09-05 | ~~**뮤즈 대시**~~ | 약 340 노트 | **약 4시간** | 이 기록 이후 **지원 제외** (작업 난이도 과다). 게임에서 확인까지 마친 유일한 프로파일(`Playtested`) |

> 게임별 레인·키 폭·홀드 판별 방식과 **검증 상태**는 [🎮 game_profiles.md](../specifications/game_profiles.md) 한 곳에서 관리합니다.
> 2026-09-16 에 스타트레일·스타게이저·건볼트·DEFLATE 의 실제 차트(MARENOIA 392노트, Discotic Night 555노트, shut up 361노트,
> どりーむもーど 552노트 등)로 한 것은 **새로 만든 채보의 작성 시간이 아니라**, 이미 있는 차트를 읽어 에디터의 짝이
> 게임 모드 코드와 같은지 대조한 검증입니다. 결과는 그 문서의 "실제 게임 차트 대조" 표에 있습니다.

### 시간 배분 (추정)

| 구간 | 추정 | 비고 |
|:---|:---:|:---|
| 음원 · BPM · 오프셋 맞추기 | 20~30분 | ⚡오프셋 자동 맞춤 첫 실사용 |
| `#WAV` 파일명(UID) 준비 · 등록 | 20~30분 | 오브젝트 종류마다 별도 파일 필요 |
| **노트 340개 배치** | **50~70분** | 붓 바꾸기 포함 노트당 8~12초 |
| **롱노트 · 샌드백 짝 맞추기와 디버깅** | **40~60분** | |
| **게임 실행 검증 → 원인 찾기 → 복귀** | **50~70분** | 배틀 진입 시 로그 385줄 |
| 되돌리기가 없어 생긴 재작업 | 20~30분 | |

**배치 자체는 한 시간 남짓입니다. 나머지 두 시간은 "맞게 찍었는지 확인하는 데" 갔습니다.**
노트를 빨리 찍게 만드는 것보다, **찍은 것이 무엇인지 화면에서 보이게 만드는 것**이 먼저입니다.

## 🔍 시간이 어디로 가는가

### 1. 노트의 종류가 화면에 보이지 않는다

여러 게임이 **노트의 종류를 노트가 아니라 `#WAV` 쪽에 적습니다.**

적는 자리는 셋뿐입니다 — **슬롯 코드 값** / **`#WAV` 파일명** / **같은 채널 안의 출현 순서**.
게임 5종이 이 셋을 전부 쓰고 있습니다. 어느 게임이 어느 방식인지는
[🎮 game_profiles.md](../specifications/game_profiles.md) 의 표 한 곳에 있습니다.

그런데 (측정 당시) 이 에디터는 그 규칙을 하나도 몰랐습니다.
[`BmsParser`](../../bms%20editer/Services/BmsParser.cs) 는 건반 채널의 모든 노트를 `NoteType.Normal` 로 읽고,
[`NoteGridControl`](../../bms%20editer/Views/Controls/NoteGridControl.cs) 은 **레인 색(빨강/파랑/흰색)만** 다르게 칠했습니다.
(→ v0.1.4: 노트는 여전히 `Normal` 이지만, 프로파일을 고르면 짝지어진 홀드가 **몸통**으로, 짝이 어긋난 노트가 **주황 점선**으로 보입니다.)

> **결과: 340개가 전부 똑같은 점으로 보였습니다.**
> 어느 것이 롱노트 시작이고 어느 것이 끝인지, 어느 것이 장애물이고 어느 것이 하트인지
> **화면에 없습니다.** 전부 머릿속과 파일명 기억으로 관리하게 됩니다.

### 2. 짝이 어긋나면 게임을 켜야만 안다

뮤즈 대시의 홀드·샌드백은 **같은 채널에서 홀수 번째가 시작, 짝수 번째가 끝**입니다
(모드의 `BmsNoteMatcher`).

> [!CAUTION]
> **중간에 홀드 하나를 끼워 넣으면 그 뒤의 모든 홀드가 시작↔끝이 뒤집힙니다.**
> 47마디를 고쳤는데 60마디부터 무너집니다. 원인과 증상이 멀리 떨어져 있습니다.

그리고 그 사실을 알려주는 곳이 **게임 로그 한 줄뿐**입니다. 그것도 채널당 마지막 하나만:

```
[BmsMatcher.Bug] 홀드 매칭 경고: 채널 13의 Tick ... 짝(종료 노트)을 찾지 못했습니다.
```

에디터는 이 규칙을 몰랐으므로 **저장할 때까지 아무 말도 하지 않았습니다.**
검증이 통째로 "게임 실행"으로 밀려나고, 왕복 한 번마다 수 분씩 나갔습니다.
(→ v0.1.4: 짝 검사기가 수열이 **처음 어긋난 자리**를 `ParityBreak` 로 지목합니다.)

### 3. 되돌리기가 없다

[known_issues.md 의 C 항목](known_issues.md#-c-undo--redo)입니다.
되돌릴 수 없으니 일괄 작업을 과감하게 못 씁니다. 대신 확인창을 읽고, 파일 사본을 만들고,
결과를 눈으로 다시 확인합니다. **이 방어 비용이 작업 내내 붙습니다.**

## 🎮 게임별로 걱정되는 자리

**플레이로 확인한 것은 뮤즈 대시 하나뿐입니다.** 나머지는 게임 모드 코드로 짝 규칙을 옮기고, 실제 차트로 대조한 단계입니다.
채보를 새로 만들어 보면 이 표를 고칩니다.

| 게임 | 검증 상태 | 걱정되는 자리 |
|:---|:---:|:---|
| ~~**뮤즈 대시**~~ | ✅ 플레이 확인 · ❌ **지원 제외** | 6자리 UID 와 출현 순서 전파(중간에 하나 끼우면 뒤가 전부 뒤집힘). 검사기가 첫 어긋난 자리를 지목하지만 작성 부담 자체는 그대로다 |
| **스타트레일** | 🔶 코드 확인 | 레인마다 대기 칸이 하나라 시작을 두 번 찍으면 앞 시작이 **조용히 버려진다**(에디터는 `ReplacedHead` 로 지목) |
| **스타게이저** | ⚠️ 가정 | 짝을 게임 엔진이 맺어서 **짝 규칙 자체가 미확인**이다. 화면의 몸통을 그대로 믿으면 안 된다 |
| **건볼트** | 🔶 코드 확인 | 홀드 끝을 여러 시작이 같이 쓸 수 있다(`SharedTail`). 페어리 시작 8종 중 무엇을 찍었는지 번호로만 구분된다 |
| **DEFLATE** | 🔶 코드 확인 | 홀드 쌍 번호가 역할과 **반대**(`00B`=시작/`00A`=끝). 실제 차트에 홀드가 없어 **홀드 규칙이 실제 차트로 확인되지 않았다** |
| **UNBEATABLE** | 🔶 코드 확인 | 출현 순서 방식이라 전파가 있다. 실제 차트에 홀드가 없어 **실제 차트로 확인되지 않았다** |

> [!NOTE]
> 게임마다 다른 노트 종류 규칙은 **게임 프로파일(JSON) 한 가지 구조**로 풀었습니다.
> 프로파일을 고르면 화면에 **홀드 몸통과 연결선, 짝 문제 표시**가 바로 나옵니다.
> → [hold_pairing_spec.md](../specifications/hold_pairing_spec.md) · [game_profiles.md](../specifications/game_profiles.md)

## 🛠️ 개선 과제 진행 현황

### A. 게임 프로파일 — 에디터가 게임의 의미를 알게 하기

키음 → 노트 종류 매핑 규칙을 **JSON 프로파일 파일**로 두고 에디터가 읽습니다.
게임이 늘어나면 프로파일만 추가합니다.

| # | 항목 | 상태 | 내용 |
|:---:|:---|:---:|:---|
| **A-1** | **짝 검사기 (Pair Linter)** | **✅ v0.1.4 완료** | 홀드·게이트·아크 짝이 맞는지 편집할 때마다 자동 검사하고 고아 노트를 지목 |
| **A-2** | **종류별 몸통 렌더링** | **✅ v0.1.4 완료** | 롱노트 시작·끝을 **반투명 몸통(Body)과 선**으로 이어 그리고, 게이트/페어리 색상 구분 |
| **A-3** | **드래그로 롱노트 배치** | 🚧 예정 | 시작~끝을 그으면 짝 2개를 자동 생성 (되돌리기 구현 후 진행) |
| **A-4** | **레인 · 팔레트 프로파일** | 🚧 예정 | 그 게임이 안 쓰는 레인은 숨기고, 팔레트를 파일명이 아니라 **의미**로 묶기 |

A-1과 A-2는 검증 왕복을 줄이려는 기능입니다. 실제로 얼마나 줄었는지는 다음 실측에서 잽니다. 남은 과제는 배치 편의성과 작업 속도(Undo/Redo)입니다.

### B. 편집 자체의 속도

| # | 항목 | 왜 |
|:---:|:---|:---|
| **B-1** | **되돌리기 / 다시 하기** | 속도 기능입니다. 이게 있어야 나머지를 과감하게 씀 |
| **B-2** | **클립보드 (Ctrl+C/X/V) · 미러 · 레인 회전** | 지금은 검색 창의 마디 단위 복제뿐 |
| **B-3** | **A-B 구간 반복 재생** | 몇 마디 검수마다 스크럽하는 왕복 제거 |
| **B-4** | **마우스로 노트 끌어 옮기기** | 지금 이동은 선택 후 방향키뿐 |
| **B-5** | **키보드 입력 · 실시간 레코딩** | 배속 0.1~1.0x 가 이미 있어 얹기 좋음 |

### 🅿️ 보류: 온셋 자동 채보

파형 온셋으로 노트를 자동 배치하는 안은 **접어 둡니다.**
온셋은 "소리가 튄 순간"만 알기 때문에 **롱노트를 잡을 수 없습니다.**
그런데 위 실측에서 시간을 먹은 것이 바로 그 롱노트였습니다. 문제의 한가운데를 비켜갑니다.

## 🚧 그때까지의 요령

지금 상태에서 시간을 덜 쓰는 방법입니다.

* **롱노트는 시작→끝을 한 쌍씩 완성하고, 중간에 끼워 넣지 않습니다.** 나중에 삽입해야 하면
  **그 뒤의 짝을 전부 다시 확인**해야 합니다.
* 홀드가 많은 구간은 **마지막에 몰아서** 찍습니다. 앞쪽 편집이 뒤쪽 짝을 흔들지 않게 합니다.
* 큰 일괄 작업 전에는 **파일 사본을 따로 만듭니다.** 되돌리기가 없고 `.bak` 은 직전 1개뿐입니다.
* 게임 로그는 **요약만 보이게** 두고 필요할 때만 Verbose 를 켭니다.
  (뮤즈 대시 모드 `0.10.5` 부터 배틀 진입 로그가 385줄 → 5줄)
